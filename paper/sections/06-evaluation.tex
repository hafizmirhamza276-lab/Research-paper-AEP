\section{Evaluation}
\label{sec:evaluation}

\begin{itemize}
\item[\textbf{RQ1}] Under crashes, does AEP eliminate \emph{undetected}
      duplicates, and what does its residual ambiguity depend on?
\item[\textbf{RQ2}] Which of the protocol's two durability mechanisms produces
      which guarantee --- and against which faults is each one observable?
\item[\textbf{RQ3}] What does the protocol cost, and how much of that cost is
      a choice?
\item[\textbf{RQ4}] How does recovery behave?
\end{itemize}

\subsection{Setup}
\label{sec:eval-setup}

\paragraph{Systems} The seven of \cref{tab:trilemma}, implemented as thin
variants over one connector, one workload driver and one oracle, so that only
the differences differ. Each carries a machine-readable descriptor that tests
check against the implementation, and a crash point that does not exist in a
given system is marked inapplicable and never run rather than silently skipped.

\paragraph{Faults} Workers are separate OS processes killed with real
\texttt{SIGKILL} at one of the six crash points of \cref{tab:crashpoints}. A
\emph{regime} is a named fault condition, not a matrix dimension, and we
report each separately because they are different experiments. Five are
reported, and each is named here with the section that reports it:

\begin{itemize}
\item \textbf{crashed}: every execution is killed at the cell's crash point.
      This is the regime RQ1 is about (\cref{sec:eval-rq1}), and it is also
      the regime of the detection ablation (\cref{sec:eval-detection}).
\item \textbf{crash-free} (\texttt{p0}): nothing is injected. The only regime
      RQ3 may use (\cref{sec:eval-rq3}).
\item \textbf{\texttt{redis-kill-preack}}: no worker crash; Redis is hard-killed
      with \texttt{docker kill -s KILL} at the instruction boundary between the
      intent CAS and the barrier acknowledgement, then restarted and verified.
      This is RQ2's ablation (\cref{sec:eval-prevention}).
\item \textbf{\texttt{redis-kill-inflight}}: the same fault armed at the last
      instruction before transmission and delivered afterwards, so that it
      lands once both arms have dispatched. It is the control for
      \texttt{redis-kill-preack}: where the fault falls on the far side of the
      branch point, the arms should tie, and they do
      (\cref{sec:eval-prevention}, under \emph{Where the fault lands after the
      branch point}).
\item \textbf{\texttt{write-loss-preack}}: no worker crash and no Redis kill;
      the block device under Redis's append-only file stops accepting writes
      while reporting success, armed at the intent checkpoint. This is the
      fault the durability claim is defined against, and the regime that
      refuted our prediction (\cref{sec:eval-writeloss-cell}).
\end{itemize}

A sixth regime, a $30\%$ crash probability, was collected and is in the
artifact; no table here quotes its rates, so it is not one of the five.

\paragraph{Oracle} A standalone mock provider records every \emph{actually
applied} mutation in a SQLite ledger (WAL, \texttt{synchronous=FULL}, one
transaction per mutation). Duplicates are counted from that ledger, never from
the system's own opinion of itself. The analysis is permitted to read exactly
two files per run, the event log and the oracle ledger, and a source gate
that parses the analysis modules fails the build if they import anything that
could reach live protocol state.

\paragraph{Statistics} Rates are over executions. Per-cell rate intervals use
a seeded run-cluster bootstrap (\BootstrapResamples{} resamples); the
B3--AEP ambiguity difference uses a stratified run-cluster bootstrap that
preserves crash-point, endpoint-capability, and keying strata. Fisher's exact
tests compare execution counts and therefore do not adjust for run clustering;
we report them descriptively, not as evidence of equivalence. Seeds and
repetition counts are recorded per run.

\paragraph{Two reporting rules we hold ourselves to} First, \emph{no pooled
table}. A rate computed across fault regimes is a property of how many runs of
each kind were collected, not of any system; our own analysis tool prints a
warning whenever more than one regime is present, and every number below names
its regime. Second, \emph{no absolute timing from an ungated host}. A run
contributes a duration only if the operator declared before the run that the
host cannot suspend \emph{and} the run's wall-versus-monotonic divergence stays
within tolerance. Both halves are necessary: a host that merely was not idle
long enough to suspend is indistinguishable from one that cannot. Under this
gate, \emph{zero} runs collected before this rule existed contribute a timing
number, and none does. Both rules were adopted after the first collection:
the pooling rule when a mid-study review found the pooled summary table
unusable as a source, the timing gate after a host suspension was discovered
mid-run. Every rate and duration below is reported under them.

\paragraph{A durable log is not enough, and the two configurations of one
engine land on two different corners} B4 has a write-ahead record,
acknowledged durable by the same \texttt{WAITAOF} barrier AEP uses. It is not
ablated on durability. It duplicates at \BfourDupPosOnly{} on
\textsc{pos-only} and \BfourDupNoReadback{} on \textsc{none}
(\BfourExecPosOnly{} and \BfourExecNoReadback{} executions), and it duplicates
on \textsc{auth} as well, at \BfourDupAuth{} over \BfourExecAuth{}
executions. The endpoint's
reconciliation capability does not rescue it. A
read-back tells a recovering workflow what the provider currently holds, and
B4's duplicate is a second application it chose to make, not a fact it failed
to look up.

B4b is the same engine with Maximum Attempts set to $1$, and it is the cleaner
half of the demonstration: over \BfourbExecPosOnly{} and
\BfourbExecNoReadback{} executions it records \emph{zero} undetected
duplicates on both classes and loses the effect in \BfourbLostPosOnly{} and
\BfourbLostNoReadback{} of them instead, and \BfourbLostAuth{} over
\BfourbExecAuth{} on \textsc{auth}. One configuration line moves
the engine from one silent corner of \cref{sec:trilemma} to the other, and
neither configuration reaches the third: across all \BfourFamilyAmbCells{}
B4 and B4b cells the declared-ambiguity rate never exceeds
\BfourFamilyAmbMax{}.

\paragraph{The engine itself was run, and it separates what B4 licenses from
what it does not} We ran the production engine against the same non-cooperative
endpoint, in the two configurations B4 and B4b instantiate, at the one crash
point both the engine and our model can be cut at. With unlimited attempts it
duplicated at \BfiveDup{} over \BfiveExec{} executions and lost effects at
\BfiveLost{}; with Maximum Attempts set to one it lost at \BfivebLost{} over
\BfivebExec{} executions and duplicated at \BfivebDup{}. Neither configuration
declared ambiguity in any of \BfiveRuns{} non-void runs (\BfiveAmb{} and
\BfivebAmb{} declarations), so the third corner of \cref{sec:trilemma} goes
unreached by the engine itself and not merely by our model of it.

\emph{The direction transfers; the magnitudes do not.} Each configuration lands
in the corner the supplementary comparison assigns it, with exactly zero events
of the other kind. But at that same crash point B4 duplicates at
\BfourAtBarrier{} over \BfourAtBarrierExec{} executions and B4b loses at
\BfourbAtBarrier{} over \BfourbAtBarrierExec{}, roughly six times the engine's
rates. \textbf{B4's rates are our model's, not the product's}, and no rate in
this paper should be read as an engine's.

Four things bound this and none is removed by having run the engine. The
comparison is \emph{incomplete}: the engine has no position answering to
\textsc{after-intent-before-barrier}, because its pre-dispatch record is written
by the server inside one RPC, so there is no worker-side instant between the
write and its acknowledgement. That is a hole exactly where B4 and B4b have
data at all three capability classes. The rates are conditional on a
\BfiveStartToClose{}\,ms Start-To-Close timeout that B4 has no analogue for; a
different timeout is a different cell, and no timing number here is any engine's
recovery latency. The interval arithmetic is asymmetric: B4's intervals rest
on three runs against the engine's thirty, and three clusters put resampled
means on multiples of one thirtieth. The separation should therefore be read
from the point estimates, which differ by roughly $0.8$, and not from the
intervals failing to overlap. And the crash window at the dispatch point is sized by the
server and by loopback rather than by the protocol, so its width is not
like-for-like with B4's.

That is the sharpest form of the argument the paper can make \emph{against our
model of a durable-execution engine}. That qualification is not modesty, and
the paragraphs above are why: B4 is our implementation
of the pattern, not a product, and we registered before collecting B5 that a
gap of that size would oblige us to re-scope every B4 claim. The shape of the
argument transfers and the magnitude is our model's. The argument is nonetheless
made against a system that has everything the write-ahead pattern is supposed to
provide. The record is necessary and it is not sufficient, because the
record cannot contain the fact that matters, which is whether the provider
applied the effect. What separates B3 and AEP-full from B4 is not durability but the
\emph{absence of an edge back into the dispatching state}: the transition
table has no path that re-enters \textsc{about-to-fire}, checked inside the
atomic script (\cref{fig:statemachine}). What separates them from B4b is that
declining to re-send is not the same as knowing whether to.

\subsubsection{The residual is set by the endpoint, not the protocol}

AEP's declared-ambiguity column is \AepAmbAuth{} on \textsc{auth},
\AepAmbPosOnly{} on \textsc{pos-only} and \AepAmbNoReadback{} on
\textsc{none}. That ordering is not a defect that better engineering would
remove; it is \cref{tab:capabilities} showing through. Where the endpoint can
prove absence, recovery resolves everything and nothing is left ambiguous.
Where it can only confirm presence, absence is uninformative and the honest
answer is ``I do not know''. Where it cannot be queried at all, no amount of
protocol recovers the fact.

\paragraph{The \textsc{pos-only} rate depends on how the read-back is keyed, and
we did not expect it to} The read-back in the cells above is keyed by the
caller's own reference. We pre-registered an alternative keying, an oracle
fingerprint of the request, as a sensitivity check, and predicted it would
leave every headline rate inside a $\pm\BthreeVsAepAmbMargin{}$ percentage-point
margin. On \textsc{pos-only} it does not: declared ambiguity is
\KeyingAmbiguityCaller{}\% under the caller's reference and
\KeyingAmbiguityOracle{}\% under the fingerprint, a difference of
\KeyingAmbiguityDelta{} percentage points, and the margin was
\BthreeVsAepAmbMargin{}.

The two columns that carry the safety claim are unmoved: undetected duplicates
and lost effects are zero under both keyings. What moves is the residual, and
the consequence is a limit on generality rather than on correctness. \emph{The
\textsc{pos-only} ambiguity rate is a property of the protocol \emph{and} of how
the recovering worker phrases its question}, so the figure quoted above should
be read as this keying's, not as the class's. \textsc{auth} is unaffected,
because a read-back that can prove absence resolves the execution whichever key
it is asked under.

The supplementary material plots the same executions as one bar pair per system,
pooled over crash points and capabilities: the three systems on the right have an
empty left bar, and only AEP-full and its ablation B3 have a right bar at all.
The figure adds no number this section does not state; the bars are Wilson
intervals on pooled counts, and the cluster-aware bootstrap intervals in the artifact's
per-cell metrics are wider and are the ones to quote.

The rate decomposes further by crash point, and that is where the protocol's
conservatism becomes visible; the supplementary material gives the full
decomposition across all six crash points and three capability classes.

Two cells carry the argument. At \texttt{before\_intent\_write} the rate is
zero in every capability class: the crash precedes the intent, nothing was
promised, and there is nothing to be ambiguous about. At
\texttt{after\_barrier\_before\_dispatch} it is at its maximum, and that is
the crash point at which \emph{no effect can possibly exist}, because the
worker died before sending anything. AEP declares ambiguity most often exactly
where it is least warranted by the world. That is the false-positive ambiguity
of \cref{sec:p2}, and its direction is the whole design: the protocol's errors
are toward saying ``I might have done something'' when it did not, never toward
silence when it did. The cells where an effect \emph{does} typically exist,
\texttt{mid\_dispatch} and \texttt{after\_response\_before\_resolution} under
\textsc{pos-only}, show low ambiguity, because a positive read-back
confirms the effect and the intent resolves.

\subsubsection{Why the provably-empty cell is not resolved}
\label{sec:eval-provable}

The \texttt{after\_barrier\_before\_dispatch} row invites an obvious
question: if the worker died before sending anything, \emph{the system
could know that}. It cannot, and the reason is the protocol's rather than
the implementation's: nothing durable distinguishes that history from one
where the worker died \emph{during} transmission with the request already
on the wire. Recovery sees an authorized, unresolved intent in both, so it
fails closed. \textbf{The cell is empty in the world and unresolvable from
the store.} The supplementary material, under \emph{Why the provably-empty
cell is not resolved}, gives the probe detail and prices the third barrier
that would split the two cases.

\subsubsection{The cost of the third corner}

Declared ambiguity is not free, and a paper that presented it as a pure win
would be selling something. Each declared ambiguity is an execution that has
stopped, that will not proceed without a human, and whose resolution requires
someone to establish out-of-band what the endpoint will not say. On a
\textsc{no-readback} endpoint under a crash-heavy regime that is most of the
crashed executions. What we claim is not that this is cheap but that it is
\emph{the honest price of the information the endpoint withholds}, and that
the alternative is not fewer incidents but the same incidents discovered later
by a different department. We have not evaluated whether operators handle
declared ambiguities well, or how much a real deployment would generate; both
are stated as gaps in \cref{sec:threats}.

\subsection{RQ2 --- which mechanism produces which guarantee}
\label{sec:eval-rq2}

AEP contains two durability mechanisms and the literature usually treats them
as one. The first is the \emph{pre-dispatch record}: an intent, written and
fenced, that exists before the external call does. The second is the
\emph{barrier}: the \texttt{WAITAOF} round trip that makes the record's
durability a checked precondition of dispatch authority (\cref{sec:p2}). B3 is
the ablation that separates them: AEP-full with the barrier removed and
nothing else removed. Running it against three different fault classes
assigns each guarantee to the mechanism that actually produces it.

The assignment is not the one we expected, and it is the paper's central
structural result.

\subsubsection{Detection is the record's, not the barrier's}
\label{sec:eval-detection}

Everything in \cref{sec:eval-rq1} survives the barrier's removal intact: zero
undetected duplicates, zero lost effects, and a residual of declared ambiguity
shaped by endpoint capability.

\input{generated/table-ablation}

Over \BthreeVsAepN{} crashed executions per arm, B3 and AEP-full show no
observed difference in either silent-failure metric. Both record an
undetected-duplicate count of $\BthreeVsAepDupCount{}$ and a lost-effect count
of $\BthreeVsAepLostCount{}$. Declared ambiguity is
\BthreeAmbCount{}/\BthreeVsAepN{} for B3 and
\AepAmbCount{}/\BthreeVsAepN{} for AEP-full; per capability class the two
systems track each other: \BthreeAmbAuth{} against \AepAmbAuth{} on \textsc{auth},
\BthreeAmbPosOnly{} against \AepAmbPosOnly{} on \textsc{pos-only},
\BthreeAmbNoReadback{} against \AepAmbNoReadback{} on \textsc{none}.

For ambiguity, B3 minus AEP-full is \BthreeVsAepAmbDiffPP{} percentage points.
The stratified run-cluster \BthreeVsAepAmbDiffConfidence{}\% interval is
[\BthreeVsAepAmbDiffLow{},\,\BthreeVsAepAmbDiffHigh{}] percentage points,
which lies within a $\pm\BthreeVsAepAmbMargin{}$ percentage-point margin. We
introduce that margin in this revision; it was not preregistered, and we state
it as a stipulation rather than derive it. We do not claim it is immaterial to
an operator: \cref{sec:threats} records that we have not evaluated declared
ambiguity as an operational outcome, and that the artifact has no escalation
mechanism, so we have no basis on which to price one. The result
supports equivalence under that stated, post hoc margin, but only for this
fixed design. Each arm has \BthreeVsAepAmbClusters{} run clusters distributed
over \BthreeVsAepAmbStrata{} matched strata, three runs per stratum, so the
cluster-aware interval is a sensitivity analysis, not a strong general
equivalence result. The execution-level Fisher value
($p = \BthreeVsAepAmbP{}$) is not used as equivalence evidence.

\textbf{A word on what the zeros can and cannot support.} Fisher's exact test
on $\BthreeVsAepDupCount{}/\BthreeVsAepN{}$ against
$\BthreeVsAepDupCount{}/\BthreeVsAepN{}$ returns
$p = \BthreeVsAepDupP{}$ for duplicates and $p = \BthreeVsAepLostP{}$ for lost
effects. Neither $p$-value carries information: a test between two zero
counts has no power, and failing to distinguish them is not evidence that they
are the same. What two zeros do support is a \emph{bound}. The unit for that bound
is the run, not the execution: each arm's \BthreeVsAepN{} executions are
\BthreeVsAepRuns{} runs of ten, and ten executions that share a run, a crash
point and a system are not ten independent trials. The one-sided
95\% Wilson upper confidence bound on a zero numerator over
\BthreeVsAepRuns{} run clusters is \AblationZeroUpperRun{}\%. This is a genuinely
one-sided bound using the 95th normal quantile; it is not the upper endpoint of
a two-sided 95\% Wilson interval, which uses the 97.5th quantile. Each system's
rate is individually bounded this way. When the two system bounds are stated
simultaneously, Bonferroni gives joint coverage of at least 90\%, not 95\%.
Under that simultaneous event, both rates lie in
$[0,\AblationZeroUpperRun{}\%]$, so their absolute difference is at most
\AblationZeroUpperRun{} percentage points. This finite-sample bound is the support
for ``no observed difference'' in the two zero-event metrics; the corresponding
Fisher values are not evidence of equivalence.

Treating the executions as independent would give
\AblationZeroUpperExec{}\%. We use the run, for the same reason the Fisher
values in \cref{tab:ablation} are not read as equivalence: with no events
observed, nothing in these data estimates the within-run correlation that
execution-level independence would require. The choice of unit decides nothing
claimed below:
the baseline duplicate rates this bound is contrasted against are
\BaselineDupLowPct{}--\BaselineDupHighPct{}\%, more than an order of magnitude
from either figure, so the conservative unit is taken because it is the
defensible one and not because the comparison needs it.

\textbf{We report this as a finding rather than as a limitation, because it
reassigns our own headline claim.} The property that distinguishes AEP from
B0, B1 and B2, and the property the paper is named for, is produced by
the pre-dispatch record and by the transition table that refuses to
re-enter \textsc{about-to-fire}. It is not produced by waiting for
\texttt{fsync}. A reader who wants the detection guarantee and not the
barrier's cost can have it, and the supplementary material prices that
configuration explicitly.

This also sharpens what B4 shows. B4 has a durable record, acknowledged by the
same barrier, and duplicates at the highest rate in the study; B3 has a durable
record, no barrier, and duplicates at zero. Durability is neither necessary nor
sufficient for detection. What is necessary is that the record be written
\emph{before} the call and that no path re-enter the dispatching state.

\subsubsection{Prevention is the barrier's, and it needs the right fault}
\label{sec:eval-prevention}

If detection does not need the barrier, what does the barrier do? It withholds
the external call when the durability of the intent can no longer be confirmed.
That is a different guarantee, it is worth stating in its own metric, and no
worker-crash fault can exercise it, which is why \cref{sec:eval-detection}
returns a null. The fault that exercises it is loss of Redis itself.

The metric is the \emph{unwanted-applied-effect rate}: the fraction of
executions in which a real, non-idempotent mutation reached the provider while
the durability of its own intent record could no longer be established. It is
not the same quantity as an undetected duplicate and it is not measured on the
same regime; keeping the two apart is what this subsection is for.

We hard-kill Redis at \texttt{after\_intent\_before\_barrier}: the instruction
boundary between the intent CAS and the acknowledgement. AEP-full is inside
\texttt{WAITAOF} at that moment; B3 is not, because B3's ablation is exactly
that round trip. One execution per run, no worker crash: the fault under
study is Redis dying.

\paragraph{The controlled fault} The result below is collected under a
\emph{controlled} injector, and that is the change that makes it worth
reporting. \texttt{docker kill} alone lands \UncontrolledLanding{}\,ms after it
is issued on this host; freezing the container first with \texttt{docker pause}
and killing it afterwards lands in \ControlledLanding{}\,ms, with a third of the
spread, and leaves the container in the same end state. The fault class does not
change, since it is the same F3 crash-stop at the same instruction boundary,
so the two are comparable, and the injector's own contribution to the race is
narrowed by measurement rather than argued away.

Over \ArmASessions{} sessions and all \ArmAClasses{} capability classes,
AEP-full's unwanted-applied rate is \ArmAAepRate{} (\ArmAAepApplied{} of
\ArmAAepN{} executions) and B3's is \ArmABthreeRate{}
(\ArmABthreeApplied{}/\ArmABthreeN{}), on the same injected fault. The
between-session spread in AEP-full's count, which a single collection cannot
see and which the earlier version of this result was criticised for not
reporting, collapses to \ArmASpreadMax{} count per class across the
\ArmASessions{} sessions. B3 stays at its ceiling throughout, never below
\ArmABthreeFloor{} of \AepKillRuns{} in any class in any session, which is what
rules out the reading that the injector simply disabled both arms.

\paragraph{The result fell below its own pre-registered bound, and we report
that as a surprise rather than a success} The prediction was registered before
the data existed: \ArmAPredicted{}, bounded [\ArmABoundLow{},
\ArmABoundHigh{}], derived from the measured landing distribution as the
fraction of a $1\,000$\,ms \texttt{WAITAOF} window the injector leaves open.
The observed \ArmAAepRate{} is \emph{below} that bound. The pre-registration
fixed in advance what a rate outside the bound would mean, namely the protocol
behaving unexpectedly and not the mechanism succeeding, and we honour that here
rather than presenting a lower-than-predicted number as a better result.

The reason the bound was wrong is measurable, and it is not calibration: the
model behind it fails on two independent premises that push in opposite
directions. First, it treats the exposure window as the injector's bench-measured
landing latency. That does not survive contact with a collection:
\ModelAcksPastLanding{} of \ModelAckN{} uncontrolled AEP-full runs received a
genuine \texttt{WAITAOF} acknowledgement \emph{after} the bench landing had
supposedly passed, and a \texttt{WAITAOF} acknowledgement requires a live
server. Timed during the collections themselves, the same injector call takes
\ModelInSituKill{}\,ms against the bench's \ModelBenchKill{}\,ms, a factor of
\ModelInSituRatio{}$\times$, with ranges that do not overlap. Second, it treats
the \texttt{WAITAOF} wait as uniform on $U(0, 1\,000)$\,ms. Measured over the
runs the model was calibrated against, the fraction of waits under
\ControlledLanding{}\,ms is \ModelEmpiricalWindow{}, where uniformity assigns
\ModelUniformWindow{}, which is \ModelUniformOverstates{}$\times$ too generous,
and worse the narrower the window. The two errors partly cancelled at the
uncontrolled window and could not at the controlled one.

The calibration that appeared to license the bound compared the wrong two
quantities. The model predicts \emph{dispatch}; the estimand is an
\emph{applied effect}, and dispatch is necessary for one without being
sufficient. On the same runs the dispatch rate is \ModelDispatchRate{} and the
applied rate is \ModelAppliedRate{}. Against the quantity it actually predicts,
the model was already wrong on its own calibration data. We record this because
a pre-registered bound that agrees for the wrong reason is worse than one that
disagrees, and only the second kind is visible without looking.

\paragraph{What this does and does not license us to say} We report a rate and
its mechanism, not a guarantee. \textbf{We do not claim that AEP-full prevents
the unwanted effect.} The residual is non-zero and is irreducible under this
fault class: freezing Redis synchronously at the checkpoint would make
\texttt{WAITAOF} unanswerable, but B3 reaches the same checkpoint and still
needs two further Redis calls, so the same freeze would stop B3 dispatching too
and the contrast would vanish because the injector had disabled both arms. What
the controlled fault buys is that the residual is now bounded by something we
measured rather than by this host's \texttt{docker} latency. As above, the
bound we derived from that measurement was itself wrong in a way the data can
show. The magnitude is not a constant of the protocol and this paper does
not offer it as one.

\paragraph{The uncontrolled cell replicates the direction, and is not pooled
with the controlled one} The original collection used \texttt{docker kill}
alone, and is kept as the uncontrolled replication. It is reported separately
rather than pooled: the two injectors have different landing distributions, and
combining them would trade a stated limitation for an unstated confound. There
the rate is \AepUnwantedRate{} for AEP-full against \BthreeUnwantedRate{} for B3
(Fisher's exact test, two-tailed, $p = \UnwantedP{}$), a difference of
\UnwantedPrevented{} executions on the same injected fault, the same
direction as the controlled cell, at a magnitude the uncontrolled injector sets.
This is the only fault in the study under which the two systems diverge;
everywhere else they differ by at most $\BthreeVsAepAmbDelta{}$ executions in
\BthreeVsAepN{} (\cref{tab:ablation}). Both systems declared ambiguity on all
\AepKillRuns{} runs: the endpoint is \textsc{no-readback}, so neither can
resolve what it does not know, and both fail closed. The difference between them
is not in what they \emph{say}, which is the detection guarantee that
\cref{sec:eval-detection} already showed does not depend on the barrier. It is
in what they did to the outside world before saying it.

\textbf{The direction replicates; the magnitude moves, which is why the
controlled cell exists.} The cell was re-collected \ReplicationSessions{}
further times under an identical configuration, and AEP-full's unwanted-applied
count ranged \ReplicationAepMin{}--\ReplicationAepMax{} out of \AepKillRuns{}
while B3 stayed at \ReplicationBthreeApplied{}/\AepKillRuns{} in every one.
Taking the session as the unit, the difference averaged
\ReplicationPreventedMean{} effects, 95\% interval
[\ReplicationPreventedLow{},\,\ReplicationPreventedHigh{}]; against that spread
the controlled cell's \ArmASpreadMax{}-count per-class spread over
\ArmASessions{} sessions is the change worth reporting. Two negative findings
travel with the cell and are not softened by being moved: attributing the
movement to kill latency did not succeed at this design's precision, and B3 is
not the negative control an earlier version of this paper reported it to be,
because its own session-level interval is far too wide to have contradicted the
mechanism whatever it had done. The supplementary material carries the
per-session tables for both: the uncontrolled counts, the four session-level
kill-latency differences with their intervals, and the same analysis for B3.
The scope of the cell is one pre-acknowledgement crash point and one host, and
the \textsc{authoritative-readback} class was subsequently collected over
\ClassSessions{} sessions at a precision inadequate to the
question.

\paragraph{Where the fault lands after the branch point, the arms tie} The
same fault delivered \emph{after} dispatch separates nothing, and we collected
that rather than inferring it. Arming the kill at the last instruction before
transmission and delivering it $200$\,ms later puts it in flight, after both
arms have already dispatched. Over \InflightSessions{} sessions the two arms
differ by at most \InflightMaxDiff{} count in any capability class, and both sit
at their ceiling. Two qualifications belong with that number. The second session
is a deterministic replay of the first rather than an independent draw. The
harness assigns seeds per cell and repetition, so where no race remains the
second collection reproduces the first exactly, which is itself the clearest
evidence that no race remains. And B3's lowest cell is
\InflightBthreeFloor{}/\AepKillRuns{}, exactly the floor below which the result
would have been read as a mis-timed injector rather than a tie; it is the
boundary, not headroom.

What is structural, across all three faults, is that the race exists for
AEP-full at all and cannot exist for B3.

\subsubsection{The barrier's durability claim, under the fault that can
actually test it}
\label{sec:eval-durability}

There remains a third thing the barrier is supposed to do, and it is the one
most readers assume it does first: protect the write-ahead record from being
lost when Redis dies. We tested that premise before building on it,
and for the fault everyone reaches for first, it is false.

\ProcessKillTrials{} trials, each phase-aligning the \texttt{everysec} timer
with a \texttt{WAITAOF} so the window under test is as wide as it can be,
writing a key \emph{without} waiting for it, hard-killing the container with
\texttt{docker kill -s KILL}, restarting, and reading back. Every kill landed
(every container came back with its \texttt{uptime} at zero) and every kill
landed inside the window (write-to-death
\ProcessKillWindowMin{}--\ProcessKillWindowMax{}\,ms against a $1\,000$\,ms
fsync period).
\textbf{Not one unfsynced write was lost: $\ProcessKillUnackLost{}$.}
% source: reports/raw/e1-durability-window.txt; Session 3B section C.2.

The mechanism is not subtle once seen. \texttt{appendfsync everysec} defers the
\texttt{fsync(2)}, \textbf{not} the \texttt{write(2)}: Redis writes the AOF
buffer to the operating system on every event-loop iteration. A
\texttt{SIGKILL} destroys the \emph{process}; the kernel and its page cache are
untouched, and a kernel that is still running flushes those bytes to disk. The
same result reappears at $n{=}\KillCanaryN{}$ inside the ablation cells above, where a
canary write made immediately before each kill survived in \AepKillCanary{} and
\BthreeKillCanary{} runs.

That narrows the claim to a named fault class --- loss of the page cache: host
power failure, kernel panic, VM destruction --- and an earlier draft of this
paper stopped there, naming a fault it had not injected. We now inject it.

\paragraph{Making the storage lose the writes} The probe is the one above with
the fault swapped. A loop-backed block device carries a \texttt{dm-flakey}
target whose \texttt{drop\_writes} feature silently discards every write bio
while serving reads correctly, which is what a storage stack looks like to a
kernel whose writes will never reach the platter. Redis 7.2.5 --- the same
build as the rest of the evaluation --- runs with its append-only file on an
ext4 filesystem over that device. Each trial writes one key through
\texttt{WAITAOF} and one without, switches the device into
\texttt{drop\_writes}, kills the server, unmounts to discard the page cache,
restores the device and reads both keys back. The switch is the instant of
power loss: what was \texttt{fsync}-ed before it is on the device, what was
still dirty is not.

Two details decide whether this measures anything. \texttt{dmsetup suspend}
freezes the filesystem and flushes outstanding I/O by default, either of which
would push the unacknowledged write out before the fault took effect and
produce a confident null; the reload runs with \texttt{--nolockfs --noflush}.
And a self-test runs first on the device alone, with no Redis in the picture: a
file \texttt{fsync}-ed before the switch must survive and one \texttt{fsync}-ed
after it must not. The probe refuses to report Redis trials unless that holds.
% source: experiments/flakey_write_loss.py; reports/raw/g2-flakey-write-loss.txt.

\paragraph{The result} The probe ran \FlakeyN{} trials in \FlakeyReplications{}
independent replications. Each replication builds the device stack from
scratch, and each \emph{trial} within it rebuilds the filesystem with
\texttt{mkfs.ext4} and starts a fresh server, so no trial can read a key a
previous trial's append-only file still holds. \textbf{Separation was perfect in
every replication}: the acknowledged record survived
\FlakeyPerRepAckSurvived{} and the unacknowledged one was destroyed
\FlakeyPerRepUnackLost{} in each, \FlakeyAckSurvived{} and \FlakeyUnackLost{}
overall. Against the same two keys under a process kill,
$\ProcessKillUnackLost{}$ were lost; the fault classes separate completely.

We give no $p$ for either comparison, and the reason is that no unit supports
one: at the trial level the test would assume an independence the shared device
stack violates and would ignore the pairing --- both records are written in the
same trial and meet the same write-loss event --- while at the replication
level, three against three, the two-sided minimum a perfectly separated result
can reach is $0.1$, which is the design's floor rather than a statement about
these data. The complete separation in every replication is the finding, and it
does not need one. The filesystem was mounted
\texttt{ext4 rw,relatime} with its journal enabled and no \texttt{nobarrier},
and the server's \texttt{appendfsync} was read back as \texttt{everysec} from
the running instance; the probe refuses to measure if either is otherwise,
because under \texttt{always} there is no unacknowledged write to lose and
under \texttt{nobarrier} a surviving acknowledged one would prove nothing.

\textbf{The barrier's durability benefit to the \emph{record} is therefore real
and now measured, and the fault class matters more than the mechanism.} What
that benefit is worth to a \emph{dispatch} is the next subsubsection's question,
and the answer there is not the one we expected. The Redis documentation's
``you may lose 1 second of data if there is a disaster''~\cite{redis-persistence}
is correct; what our two probes add is that ``disaster'' must mean the host,
that the widely repeated reading of the sentence as covering a crashed Redis
\emph{process} is wrong, and that once the host is the fault the sentence is
exactly right.

One qualification, and it is the same one the process-kill probe carries: the
exposure window is deliberately maximised. The unacknowledged write is issued
\FlakeyWindowMin{}--\FlakeyWindowMax{}\,ms before the device stops accepting
writes, inside a $1\,000$\,ms fsync period that a preceding \texttt{WAITAOF}
has just reset. \FlakeyUnackLost{} is therefore the loss probability for a
power cut placed where it does the most damage, not the rate a uniformly-timed
one would produce; that rate is bounded above by it and approaches it as the
write approaches the start of the period. The design is deliberate and it is
the same design that made the process-kill probe's $\ProcessKillUnackLost{}$
strong: both probes
give the loss hypothesis its best case, and only one of them finds loss.

\subsubsection{Running the protocol under that fault, and what it refuted}
\label{sec:eval-writeloss-cell}

The probe above tests \texttt{WAITAOF}, not AEP. It runs two Redis keys against
a device that stops accepting writes; it does not run AEP-full and B3 through
the harness under that fault, and so it measures no difference in \emph{protocol}
outcomes. What it establishes is the premise the durability argument rests on.
We then ran the extension, and it is reported here rather than as a caveat
because it refuted what we predicted.

\paragraph{What was registered, and what happened} We pre-registered that
AEP-full would withhold dispatch when its write-ahead record was destroyed and
that B3 would proceed. A full session was collected with the harness's Redis
running its append-only file on the flakey device: both arms,
\WriteLossRunsPerArm{} runs each, \WriteLossExecPerRun{} executions per run,
\texttt{drop\_writes} armed at the intent checkpoint, without a delivery
failure. \textbf{The prediction is refuted.} AEP-full applied an effect in
\WriteLossAepApplied{} of \WriteLossExecPerArm{} executions and B3 in
\WriteLossBthreeApplied{}; both arms finished at ceiling, and neither withheld.

\paragraph{Why, and it is the more useful finding} \textbf{\texttt{WAITAOF}
returned success for every durability acknowledgement requested after the device
had stopped accepting writes} --- \WriteLossAcksAfterFault{} of them, with
\WriteLossAckFailures{} failures. \texttt{dm-flakey}'s \texttt{drop\_writes}
discards each write bio and reports success, so the kernel sees no error,
\texttt{fsync(2)} succeeds, and Redis has no way to learn otherwise. The barrier
withholds dispatch on a \emph{failed or absent} acknowledgement; it was handed a
successful one and dispatched, behaving exactly as specified on an input that
was false.

\paragraph{The bounds, stated narrowly} \textbf{This is not evidence that the
barrier fails to withhold under write loss}: the condition the experiment exists
to create --- the barrier meeting an acknowledgement that fails or never arrives
--- was never reached, so no run exercised withholding. \textbf{Neither is it
evidence that the barrier works.} What it establishes is that the durability
guarantee rests on an unstated premise --- that a \texttt{WAITAOF} success means
the record reached the device --- and that under storage which discards writes
\emph{silently} the premise is false and the protocol cannot detect it. Storage
returning \texttt{EIO} would let the acknowledgement fail and put the barrier
back on the input its guarantee is defined over, so this result bounds the
guarantee to storage that reports its own failures and says nothing about
storage that does not. It is evidence about storage, not about the protocol. One
host, one Redis version (7.2.5, \texttt{appendfsync everysec}), and we claim it
for no other.

Only crash-free runs on a suspend-disabled host contribute. The provider is
configured with a constant $2\,000$\,ms delay, so one round trip is the floor
and the interesting quantity is the increment over it.

\textbf{So the decomposition supports an ordering and not a partition.} The
barrier dominates: its interval is nowhere near zero and the residual's
contains it under both readings. What cannot be said is what fraction of the
protocol's cost is optional, because at this precision the non-barrier
remainder is not distinguishable from nothing at all. An earlier draft of this
paper quoted that remainder as a point figure of about thirty milliseconds; it
rested on three runs per arm, and twelve more did not confirm it.

Read against \cref{sec:eval-detection} the ordering still says something
stronger than ``AEP costs two seconds''. Whatever the detection guarantee
costs, it is the difference between B0 and B3 --- B3 is the system that already
has that guarantee in full --- and it is small enough that fifteen runs cannot
separate it from zero. The \BarrierCostFifteen{}\,ms buys the prevention
guarantee of \cref{sec:eval-prevention} and nothing else.

That figure is also a property of a \emph{configuration}, not of AEP. Under
\texttt{appendfsync everysec} an acknowledgement cannot return until the next
scheduled fsync, and those are one second apart, so a barrier costs up to a
second and the protocol pays that twice. The measured total sits near the top
of that range rather than in the middle of it; the reason is unmeasured.

\paragraph{The barrier is a deployment choice, and the supplementary
prices it} The $\approx 2$-second figure above is the one a reader would
carry away as ``AEP's overhead''. It is not: it is the price of one of the
protocol's two guarantees, under one of the durability settings that
guarantee can be bought at. The supplementary material, under \emph{The
barrier is a deployment choice}, gives the three measured points as a
deployment faces them --- \texttt{everysec} with the barrier,
\texttt{always} with the barrier, and the barrier removed --- with the
table they are read from. The claim this section rests on does not depend
on it: the barrier costs \BarrierCostFifteen{}\,ms under \texttt{everysec}
and \BarrierCostAlwaysFortyFive{}\,ms under \texttt{always}, and both
figures are stated above with their intervals.
\subsection{RQ4 --- recovery}
\label{sec:eval-rq4}

Recovery is reported as counts. In the crashed regime, every interrupted
execution that had written an intent was resolved to a terminal
classification: \RecoveryAepResolved{} of \RecoveryAepAttempted{} for
AEP-full and \RecoveryBthreeResolved{} of \RecoveryBthreeAttempted{} for B3,
over \RecoveryCrashPoints{} crash points and \RecoveryClasses{} endpoint
capabilities. The classes those executions resolved to are the ones
\cref{tab:outcomes} already reports.

The sixth crash point is counted separately, and it is not a recovery
failure. At \path{before_intent_write} the worker dies before any intent
exists, so there is no record for recovery to act on
(\cref{tab:crashpoints}). The \RecoveryAepNoRecord{} executions there for
AEP-full and the \RecoveryBthreeNoRecord{} for B3 resolve to no terminal
classification at all. Pooling them with
the rest would produce a figure that reads as a failure rate for a component
that was never given anything to do.

We report no rate and no interval for this. The runs behind each cell
resolved identically, so a bootstrap interval would be degenerate and would
claim a precision they cannot support; the counts are the stronger statement.
Absolute recovery latency is not reported either. Under the timing gate of
\cref{sec:eval-setup}, \RunsWithUsableTiming{} of \RunsCollected{} runs
contribute a duration, which leaves too few gated crashed runs for a
distribution, and \cref{sec:threats} records that as a cost of the gate. The
baselines declare no recovery service and are excluded from these counts
rather than scored; the supplementary material, under \emph{RQ4: recovery},
gives that argument in full and carries the one reconciliation disagreement
in \RunsCollected{} runs and what became of it.
