\section{Evaluation}
\label{sec:evaluation}

\begin{itemize}
\item[\textbf{RQ1}] Under crashes, does AEP eliminate \emph{undetected}
      duplicates, and what does its residual ambiguity depend on?
\item[\textbf{RQ2}] Which of the protocol's two durability mechanisms produces
      which guarantee --- and against which faults is each one observable?
\item[\textbf{RQ3}] What does the protocol cost, and how much of that cost is
      a choice?
\item[\textbf{RQ4}] How does recovery behave?
\end{itemize}

\subsection{Setup}
\label{sec:eval-setup}

\paragraph{Systems} The seven of \cref{tab:trilemma}, implemented as thin
variants over one connector, one workload driver and one oracle, so that only
the differences differ. Each carries a machine-readable descriptor that tests
check against the implementation, and a crash point that does not exist in a
given system is marked inapplicable and never run rather than silently skipped.

\paragraph{Faults} Workers are separate OS processes killed with real
\texttt{SIGKILL} at one of the six crash points of \cref{tab:crashpoints}. A
\emph{regime} is a named fault condition --- not a matrix dimension --- and we
report each separately because they are different experiments:

\begin{itemize}
\item \textbf{crashed}: every execution is killed at the cell's crash point.
      This is the regime RQ1 is about.
\item \textbf{crash-free} (\texttt{p0}): nothing is injected. The only regime
      RQ3 may use.
\item \textbf{\texttt{redis-kill-preack}}: no worker crash; Redis is hard-killed
      with \texttt{docker kill -s KILL} at the instruction boundary between the
      intent CAS and the barrier acknowledgement, then restarted and verified.
      This is RQ2's ablation.
\end{itemize}

\paragraph{Oracle} A standalone mock provider records every \emph{actually
applied} mutation in a SQLite ledger (WAL, \texttt{synchronous=FULL}, one
transaction per mutation). Duplicates are counted from that ledger, never from
the system's own opinion of itself. The analysis is permitted to read exactly
two files per run --- the event log and the oracle ledger --- and a source gate
that parses the analysis modules fails the build if they import anything that
could reach live protocol state.

\paragraph{Statistics} Rates are over executions, with cluster-aware bootstrap
95\% confidence intervals (10\,000 resamples, seeded) and Fisher's exact test
for rate comparisons. Seeds and repetition counts are recorded per run.

\paragraph{Two reporting rules we hold ourselves to} First, \emph{no pooled
table}. A rate computed across fault regimes is a property of how many runs of
each kind were collected, not of any system; our own analysis tool prints a
warning whenever more than one regime is present, and every number below names
its regime. Second, \emph{no absolute timing from an ungated host}. A run
contributes a duration only if the operator declared before the run that the
host cannot suspend \emph{and} the run's wall-versus-monotonic divergence stays
within tolerance. Both halves are necessary: a host that merely was not idle
long enough to suspend is indistinguishable from one that cannot. Under this
gate, \emph{zero} runs collected before this rule existed contribute a timing
number, and none does.

\BfourbLostNoReadback{} of them instead. One configuration line moves
the engine from one silent corner of \cref{sec:trilemma} to the other, and
neither configuration reaches the third: B4 and B4b declare ambiguity in
$0.0000$ of executions everywhere measured.

That is the sharpest form of the argument the paper can make, because it is
made against a system that has everything the write-ahead pattern is supposed
to provide. The record is necessary and it is not sufficient, because the
record cannot contain the fact that matters --- whether the provider applied
the effect. What separates B3 and AEP-full from B4 is not durability but the
\emph{absence of an edge back into the dispatching state}: the transition
table has no path that re-enters \textsc{about-to-fire}, checked inside the
atomic script (\cref{fig:statemachine}). What separates them from B4b is that
declining to re-send is not the same as knowing whether to.

\subsubsection{The residual is set by the endpoint, not the protocol}

AEP's declared-ambiguity column is \AepAmbAuth{} on \textsc{auth},
\AepAmbPosOnly{} on \textsc{pos-only} and \AepAmbNoReadback{} on
\textsc{none}. That ordering is not a defect that better engineering would
remove; it is \cref{tab:capabilities} showing through. Where the endpoint can
prove absence, recovery resolves everything and nothing is left ambiguous.
Where it can only confirm presence, absence is uninformative and the honest
answer is ``I do not know''. Where it cannot be queried at all, no amount of
protocol recovers the fact.

\Cref{tab:ambiguity-by-crashpoint} decomposes this further, and it is where the

\input{generated/table-ambiguity-by-crashpoint}

Two cells carry the argument. At \texttt{before\_intent\_write} the rate is
$0$ in every capability class: the crash precedes the intent, nothing was
promised, and there is nothing to be ambiguous about. At
\texttt{after\_barrier\_before\_dispatch} it is at its maximum --- and that is
the crash point at which \emph{no effect can possibly exist}, because the
worker died before sending anything. AEP declares ambiguity most often exactly
where it is least warranted by the world. That is the false-positive ambiguity
of \cref{sec:p2}, and its direction is the whole design: the protocol's errors
are toward saying ``I might have done something'' when it did not, never toward
silence when it did. The cells where an effect \emph{does} typically exist ---
\texttt{mid\_dispatch} and \texttt{after\_response\_before\_resolution} under
\textsc{pos-only} --- show low ambiguity, because a positive read-back
confirms the effect and the intent resolves.

\subsubsection{Why the provably-empty cell is not resolved, and what it would
cost}
\label{sec:eval-provable}

The \texttt{after\_barrier\_before\_dispatch} row invites an obvious question:
if the worker died before sending anything, \emph{the system could know that}.
Why is the outcome ambiguous rather than a confirmed non-event?

Because nothing durable records it. The last durable write before the call is
the dispatch authorization, and the runner then performs preflight, mints the
capability and calls the connector without touching Redis again. A recovery
process reading the store afterwards sees an authorized, unresolved intent ---
and that is exactly what it would see had the worker died \emph{during}
transmission. The two histories are identical in the store, so recovery fails
closed, which is the correct behaviour given what it can observe.

Closing the gap is possible and we did not do it: a third durable barrier
immediately before transmission would split the two cases and let recovery
refute the earlier one. The measured price of a barrier on this configuration
is \BarrierCostEach{}\,ms (\cref{sec:eval-rq3}), so that is roughly a 50\%
latency increase to convert one crash point's declared ambiguities into
confirmed non-events --- and it narrows rather than closes the window, since a
crash between that barrier and the socket write returns the same ambiguity.
We record the trade rather than take it, and note that its value depends
entirely on the deployment's ratio of crash points, which our uniform matrix
deliberately does not model.

\subsubsection{The cost of the third corner}

Declared ambiguity is not free, and a paper that presented it as a pure win
would be selling something. Each declared ambiguity is an execution that has
stopped, that will not proceed without a human, and whose resolution requires
someone to establish out-of-band what the endpoint will not say. On a
\textsc{no-readback} endpoint under a crash-heavy regime that is most of the
crashed executions. What we claim is not that this is cheap but that it is
\emph{the honest price of the information the endpoint withholds}, and that
the alternative is not fewer incidents but the same incidents discovered later
by a different department. We have not evaluated whether operators handle
declared ambiguities well, or how much a real deployment would generate; both
are stated as gaps in \cref{sec:threats}.

\subsection{RQ2 --- which mechanism produces which guarantee}
\label{sec:eval-rq2}

AEP contains two durability mechanisms and the literature usually treats them
as one. The first is the \emph{pre-dispatch record}: an intent, written and
fenced, that exists before the external call does. The second is the
\emph{barrier}: the \texttt{WAITAOF} round trip that makes the record's
durability a checked precondition of dispatch authority (\cref{sec:p2}). B3 is
the ablation that separates them --- AEP-full with the barrier removed and
nothing else removed --- and running it against three different fault classes
assigns each guarantee to the mechanism that actually produces it.

The assignment is not the one we expected, and it is the paper's central
structural result.

\subsubsection{Detection is the record's, not the barrier's}
\label{sec:eval-detection}

Everything in \cref{sec:eval-rq1} --- zero undetected duplicates, zero lost
effects, a residual of declared ambiguity shaped by endpoint capability ---
survives the barrier's removal intact.

\input{generated/table-ablation}

Over \BthreeVsAepN{} crashed executions per arm, B3 and AEP-full behave the
same on every metric the trilemma is defined in terms of. Both record an
undetected-duplicate rate of $0$ and a lost-effect rate of $0$; declared
ambiguity differs by two executions in six hundred
($p = \BthreeVsAepAmbP{}$), and per capability class the two systems track
each other: \BthreeAmbAuth{} against \AepAmbAuth{} on \textsc{auth},
\BthreeAmbPosOnly{} against \AepAmbPosOnly{} on \textsc{pos-only},
\BthreeAmbNoReadback{} against \AepAmbNoReadback{} on \textsc{none}.

\textbf{A word on what the zeros can and cannot support.} Fisher's exact test
on $0/\BthreeVsAepN{}$ against $0/\BthreeVsAepN{}$ returns
$p = \BthreeVsAepDupP{}$ for duplicates and $p = \BthreeVsAepLostP{}$ for lost
effects, and both numbers are worth nothing: a test between two zero counts
has no power, and failing to distinguish them is not evidence that they are
the same. What two zeros do support is a \emph{bound}. The one-sided
95\% Wilson limit on a zero numerator over \BthreeVsAepN{} executions is
\AblationZeroUpper{}\%, so each system's true undetected-duplicate and
lost-effect rate is below that, and the difference between the two systems is
below it as well. That is the equivalence claim we make: not that the barrier
provably changes nothing, but that whatever it changes about \emph{detection}
is smaller than \AblationZeroUpper{} percentage points, against baselines that
differ from both by \BaselineDupLow{}--\BaselineDupHigh{}. A barrier
contributing less than \AblationZeroUpper{}\% to a quantity where the
alternative mechanisms contribute $77$--$83$\% is, for the purposes of the
design decision in \cref{sec:eval-deployment}, contributing nothing.

\textbf{We report this as a finding rather than as a limitation, because it
reassigns our own headline claim.} The property that distinguishes AEP from
B0, B1 and B2 --- and the property the paper is named for --- is produced by
the durable pre-dispatch record and by the transition table that refuses to
re-enter \textsc{about-to-fire}. It is not produced by waiting for
\texttt{fsync}. A reader who wants the detection guarantee and not the
barrier's cost can have it, and \cref{sec:eval-deployment} prices that
configuration explicitly.

This also sharpens what B4 shows. B4 has a durable record, acknowledged by the
same barrier, and duplicates at the highest rate in the study; B3 has a durable
record, no barrier, and duplicates at zero. Durability is neither necessary nor
sufficient for detection. What is necessary is that the record be written
\emph{before} the call and that no path re-enter the dispatching state.

\subsubsection{Prevention is the barrier's, and it needs the right fault}
\label{sec:eval-prevention}

If detection does not need the barrier, what does the barrier do? It withholds
the external call when the durability of the intent can no longer be confirmed.
That is a different guarantee, it is worth stating in its own metric, and no
worker-crash fault can exercise it --- which is why \cref{sec:eval-detection}
returns a null. The fault that exercises it is loss of the coordinator itself.

We hard-kill Redis at \texttt{after\_intent\_before\_barrier}: the instruction
boundary between the intent CAS and the acknowledgement. AEP-full is inside
\texttt{WAITAOF} at that moment; B3 is not, because B3's ablation is precisely
that round trip. One execution per run, \AepKillRuns{} runs per system, no
worker crash --- the fault under study is Redis dying.

The metric is the \emph{unwanted-applied-effect rate}: the fraction of
executions in which a real, non-idempotent mutation reached the provider while
the durability of its own intent record could no longer be established. It is
not the same quantity as an undetected duplicate and it is not measured on the
same regime; keeping the two apart is the whole point of this subsection.

The unwanted-applied-effect rate is \AepUnwantedRate{} for AEP-full and
\BthreeUnwantedRate{} for B3 (Fisher's exact test, two-tailed,
$p = \UnwantedP{}$). That is \textbf{\UnwantedPrevented{} real, non-idempotent
effects} that AEP-full did not commit and B3 did, on the same injected fault,
bought by one round trip --- and note that this is the only fault in the study
under which the two systems diverge. Everywhere else they differ by at most
two executions in six hundred (\cref{tab:ablation}).

Two honest qualifications. First, \emph{AEP-full still applied
\AepKillApplied{}}. The kill is asynchronous and takes $400$--$1\,000$\,ms to
land, so in roughly a third of runs \texttt{WAITAOF} completed before Redis
died and AEP-full held a genuine acknowledgement and dispatched correctly. That
is the race the fault creates, not a protocol failure, and we report it as it
came out rather than widening the window until it looks better. Second, and for
the same reason, \emph{the effect size is a property of this host's
\texttt{docker} latency}. A faster kill pushes AEP-full toward $0$ and widens
the gap; a slower one narrows it. The \emph{direction} is structural --- B3
cannot be protected by a barrier it does not wait for --- but the magnitude
should not be read as a constant of the protocol.

Third: \emph{both systems declared ambiguity on all \AepKillRuns{}}. The
endpoint is \textsc{no-readback}, so neither can resolve what it does not know,
and both fail closed. The difference between them is not in what they
\emph{say} --- that is the detection guarantee, and \cref{sec:eval-detection}
already showed it does not depend on the barrier --- it is in what they did to
the outside world before saying it.

\subsubsection{The barrier's durability claim, under the fault that can
actually test it}
\label{sec:eval-durability}

There remains a third thing the barrier is supposed to do, and it is the one
most readers assume it does first: protect the write-ahead record from being
lost when the coordinator dies. We tested that premise before building on it,
and for the fault everyone reaches for first, it is false.

Ten trials, each phase-aligning the \texttt{everysec} timer with a
\texttt{WAITAOF} so the window under test is as wide as it can be, writing a
key \emph{without} waiting for it, hard-killing the container with
\texttt{docker kill -s KILL}, restarting, and reading back. Every kill landed
(\texttt{uptime} $=0$\,s afterwards in all ten) and every kill landed inside the
window (write-to-death $419$--$992$\,ms against a $1\,000$\,ms fsync period).
\textbf{Not one unfsynced write was lost: $0/10$.}
% source: reports/raw/e1-durability-window.txt; Session 3B section C.2.

The mechanism is not subtle once seen. \texttt{appendfsync everysec} defers the
\texttt{fsync(2)}, \textbf{not} the \texttt{write(2)}: Redis writes the AOF
buffer to the operating system on every event-loop iteration. A
\texttt{SIGKILL} destroys the \emph{process}; the kernel and its page cache are
untouched, and a kernel that is still running flushes those bytes to disk. The
same result reappears at $n{=}60$ inside the ablation cells above, where a
canary write made immediately before each kill survived in \AepKillCanary{} and
\BthreeKillCanary{} runs.

That narrows the claim to a named fault class --- loss of the page cache: host
power failure, kernel panic, VM destruction --- and an earlier draft of this
paper stopped there, naming a fault it had not injected. We now inject it.

\paragraph{Making the storage lose the writes} The probe is the one above with
the fault swapped. A loop-backed block device carries a \texttt{dm-flakey}
target whose \texttt{drop\_writes} feature silently discards every write bio
while serving reads correctly, which is what a storage stack looks like to a
kernel whose writes will never reach the platter. Redis 7.2.5 --- the same
build as the rest of the evaluation --- runs with its append-only file on an
ext4 filesystem over that device. Each trial writes one key through
\texttt{WAITAOF} and one without, switches the device into
\texttt{drop\_writes}, kills the server, unmounts to discard the page cache,
restores the device and reads both keys back. The switch is the instant of
power loss: what was \texttt{fsync}-ed before it is on the device, what was
still dirty is not.

Two details decide whether this measures anything. \texttt{dmsetup suspend}
freezes the filesystem and flushes outstanding I/O by default, either of which
would push the unacknowledged write out before the fault took effect and
produce a confident null; the reload runs with \texttt{--nolockfs --noflush}.
And a self-test runs first on the device alone, with no Redis in the picture: a
file \texttt{fsync}-ed before the switch must survive and one \texttt{fsync}-ed
after it must not. The probe refuses to report Redis trials unless that holds.
% source: experiments/flakey_write_loss.py; reports/raw/g2-flakey-write-loss.txt.

\paragraph{The result} Over \FlakeyN{} trials in \FlakeyReplications{}
independent replications, each rebuilding the device and the filesystem from
scratch, the acknowledged record survived \FlakeyAckSurvived{} and the
unacknowledged one was destroyed \FlakeyUnackLost{}
($p = \FlakeyBarrierP{}$). Against the same two keys under a process kill ---
$0/10$ lost --- the fault classes separate at
$p = \FlakeyVsProcessKillP{}$. The filesystem was mounted
\texttt{ext4 rw,relatime} with its journal enabled and no \texttt{nobarrier},
and the server's \texttt{appendfsync} was read back as \texttt{everysec} from
the running instance; the probe refuses to measure if either is otherwise,
because under \texttt{always} there is no unacknowledged write to lose and
under \texttt{nobarrier} a surviving acknowledged one would prove nothing.

\textbf{The barrier's durability benefit is therefore real and now measured,
and the fault class matters more than the mechanism.} The Redis documentation's
``you may lose 1 second of data if there is a disaster''~\cite{redis-persistence}
is correct; what our two probes add is that ``disaster'' must mean the host,
that the widely repeated reading of the sentence as covering a crashed Redis
\emph{process} is wrong, and that once the host is the fault the sentence is
exactly right.

One qualification, and it is the same one the process-kill probe carries: the
exposure window is deliberately maximised. The unacknowledged write is issued
\FlakeyWindowMin{}--\FlakeyWindowMax{}\,ms before the device stops accepting
writes, inside a $1\,000$\,ms fsync period that a preceding \texttt{WAITAOF}
has just reset. \FlakeyUnackLost{} is therefore the loss probability for a
power cut placed where it does the most damage, not the rate a uniformly-timed
one would produce; that rate is bounded above by it and approaches it as the
write approaches the start of the period. The design is deliberate and it is
the same design that made the process-kill probe's $0/10$ strong: both probes
give the loss hypothesis its best case, and only one of them finds loss.

\subsection{RQ3 --- cost, and how much of it is optional}
\label{sec:eval-rq3}

Only crash-free runs on a suspend-disabled host contribute. The provider is
configured with a constant $2\,000$\,ms delay, so one round trip is the floor
and the interesting quantity is the increment over it.

\input{generated/table-latency}

\textbf{The overhead is the barrier, and nothing else.} A median step costs
\AepStepMedian{}\,ms under AEP-full against \BzeroStepMedian{}\,ms under B0,
which does nothing but call the provider. Almost all of that gap is one
mechanism. Everything the write-ahead protocol does apart from waiting for
\texttt{fsync} --- the intent ledger, the vault, the request binding, the
preflight, the recovery service --- costs \ProtocolMinusBarrier{}\,ms on a
two-second call, or \ProtocolMinusBarrierPct{}\%. The two \texttt{WAITAOF}
round trips cost \BarrierCost{}\,ms between them, or \BarrierCostEach{}\,ms
each.
% All four from generated/numbers.tex: B3-B0 and AEP-B3 on
% latency-and-throughput.csv, crash-free E5-gated runs only.

Read against \cref{sec:eval-detection} that decomposition says something
stronger than ``AEP costs two seconds''. The \ProtocolMinusBarrier{}\,ms is
what the detection guarantee costs, because \ProtocolMinusBarrier{}\,ms is the
difference between B0 and B3 and B3 is the system that already has the
detection guarantee in full. The \BarrierCost{}\,ms buys the prevention
guarantee of \cref{sec:eval-prevention} and nothing else.

That figure is also a property of a \emph{configuration}, not of AEP. Under
\texttt{appendfsync everysec} a write must wait for the next scheduled fsync,
and those are one second apart; a mean wait of half a second per barrier, twice,
is precisely what we measure. B4 and B4b landing on the same figure with their
own two acknowledged appends is independent confirmation that the cost is the
barrier and not anything AEP does around it.

\subsubsection{The barrier is a deployment choice, with three measured points}
\label{sec:eval-deployment}

The $\approx 2$-second figure above is the one a reader would carry away as
``AEP's overhead''. It is not: it is the price of one of the protocol's two
guarantees, under one of the durability settings that guarantee can be bought
at. \Cref{tab:deployment} is the decision as a deployment actually faces it.

\input{generated/table-deployment-choice}

Three points, and the third is the one the earlier framing of this paper
concealed.

\paragraph{\texttt{everysec} with the barrier} The default, and the expensive
one. An acknowledgement must wait for the next scheduled fsync, up to a second
away, and the protocol waits twice.

\paragraph{\texttt{always} with the barrier} The identical crash-free cells ---
same systems, endpoint, regime, seeds, host and provider --- against a Redis
whose only changed line is \texttt{appendfsync always}.
% source: reports/raw/f0iii-appendfsync-always.txt and the G2 re-run that
% added the B3 arm; both refuse to proceed unless CONFIG GET appendfsync
% reads back 'always' on the live server.
The barrier's cost falls from \BarrierCost{}\,ms to \BarrierCostAlways{}\,ms
--- a factor of \BarrierCostRatio{} --- for one line of configuration, because
under \texttt{always} the fsync has already happened by the time the write
returns, so \texttt{WAITAOF} has nothing left to wait for.

Both figures are ablation differences \emph{within} one policy, which required
collecting the barrier-less arm twice. It would have been easier to subtract
the \texttt{everysec} B3 median from the \texttt{always} AEP-full median, and
that would have assumed the ablated protocol's own writes cost the same under
both policies. They nearly do --- B3 is \BthreeStepMedian{}\,ms under
\texttt{everysec} and \BthreeAlwaysMedian{}\,ms under \texttt{always} --- but
``nearly'' is a measurement, and a factor of \BarrierCostRatio{} resting on an
unmeasured premise is the kind of number this paper is trying not to publish.

\paragraph{B3-mode: the barrier removed entirely} This row is not a baseline
we are beating; it is a supported configuration of the same implementation, and
\cref{sec:eval-detection} is what licenses putting it in this table. It pays
\ProtocolMinusBarrier{}\,ms over a system with no protocol at all, and it
delivers the entire detection guarantee of \cref{tab:outcomes} --- every rate
in that table, on every capability class, statistically indistinguishable from
AEP-full's. What it forfeits is \cref{sec:eval-prevention}: under coordinator
loss it will put an effect on the wire that AEP-full withholds, at
\BthreeUnwantedRate{} against \AepUnwantedRate{}, and its intent record will
not survive a host-level write loss (\cref{sec:eval-durability}).

\textbf{So the question a deployment answers is not ``can we afford AEP'' but
``do we need prevention, and at which fsync policy''.} If the coordinator is
the fault to worry about --- a Redis on the same host as the workers, an
unreplicated instance, a VM that can vanish --- the barrier is the point of the
protocol and \texttt{always} makes it nearly free at this workload's shape. If
the coordinator is well protected and worker crashes are the fault of concern,
B3-mode gives the paper's headline result for \ProtocolMinusBarrier{}\,ms.

\textbf{One measurement this table does not support.} It says nothing about
what \texttt{always} costs under load, and we are not recommending it on this
evidence. The Redis documentation calls \texttt{always} ``very very slow, very
safe''~\cite{redis-persistence}, and that judgement is about write throughput,
which our workload cannot exercise: two workers, a two-second provider delay,
and a handful of writes per step leave the system latency-bound and nowhere
near an fsync-rate limit. Our throughput figure is in fact \emph{higher} under
\texttt{always} ($0.42$ versus $0.33$ executions/s), which is a statement about
this workload's shape and not about Redis. A write-heavy deployment would land
somewhere else on the curve entirely, and finding where is not something this
evaluation attempted.

\subsection{RQ4 --- recovery}
\label{sec:eval-rq4}

Recovery behaviour is reported through the outcome distribution rather than a
success rate, for a reason worth stating: ``recovery success'' means two
different things either side of whether a recovery service was running. Where
one ran, a crashed execution reaching a terminal classification was
\emph{recovered}. Where none ran --- B0, B1, B2, B4, B4b declare none --- the
same execution reached its classification because a supervisor ran the step
again, which is not recovery but the thing recovery exists to avoid. Our
analysis excludes runs without a recovery service from that metric rather than
scoring them zero or one, because both would be statements about a component
that was not present.

Within that scope: every AEP-full and B3 execution in the crashed regime
reached a terminal classification, and across \RunsCollected{} runs exactly
one recorded a reconciliation disagreement --- every other run's own event log
agreed with its independently written oracle ledger.
% source: analysis/coverage.json and the per-run reconcile step.

That one is worth stating precisely, because the check exists to be believed.
It was a B4b cell in which the system classified all ten executions
\textsc{confirmed-applied} while the provider's ledger recorded two, eight
disagreements of the form ``the system asserted the effect was applied and the
ledger records none''. Both sibling runs of the same cell recorded ten, the
provider logged no error, and its run-log held three lines against eleven for
each sibling --- so the provider recorded almost nothing while answering the
workers successfully. We could not determine the cause. A re-run of the
identical cell, same seed and same configuration, agreed.

We treat it as a \emph{void} run on the rule the durability probe uses: a
trial whose measurement precondition failed says nothing about the system in
either direction. Counting it would let a broken ground truth set a baseline's
rate; discarding it quietly and keeping the re-run would be re-running until
the number looks right. So the re-run is what \cref{tab:outcomes} contains,
the voided attempt ships in the artifact under \texttt{results/voided/} with
this explanation beside it, and the count above is one rather than zero.
Recovery latency is not reported as an absolute figure: the E5 gate leaves too
few gated crashed runs to support a distribution, and \cref{sec:threats}
records this as a gap rather than filling it with ungated numbers.
