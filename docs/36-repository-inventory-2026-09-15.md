# 36. Repository inventory — what is here, what is deliberately not, and where the rest lives

**Written 2026-09-15, phase 34, before the Zenodo deposit.**

This document exists because phase 20 spent several hours believing destroyed
data was unrecoverable while two verified copies sat on the same host. The
repository named them — `ARTIFACT.md` §5 did, in tracked text — and nobody read
it. **A repository that describes an artefact but never locates it protects the
data and not the reader.** This is the locating document.

It is also what the deposit must carry: §4 lists 852 MB of collection trees the
existing archive does **not** cover.

## 2. What is ignored, and why

### 2.1 Raw run directories — 19 128 files, `.gitignore:128`

1 096 run directories under `experiments/results/**`. The rule states it
plainly: *"never a run directory, never a sqlite ledger, never a log"*. They are
the evaluation and are published as an **archive**, not committed.

What *is* tracked from each root: `MANIFEST.csv`, `MANIFEST.md`, `SHA256SUMS`,
`RAW-SHA256SUMS`, and the named analysis products `check_paper_numbers.py`
reads. Fourteen roots carry a `RAW-SHA256SUMS` binding every file in every run
by digest:

```
b2-2026-08-21  b2-s1-2026-08-21  b2-s2-2026-08-21  b2-s3-2026-08-21
matrix         fsync-always-2026-09-14
phase10-replication-{drvfs,drvfs-arbb30,ext4,ext4-arbb30}-2026-09-02
ws5-2026-09-10/{t1-p0-everysec,t1-incomplete,t2-p30,t2-keying}
```

**`experiments/results/fsync-always` has no `RAW-SHA256SUMS`** — it is the
August three-run cell whose raw tree this checkout has never held. See §4 and
`RAW-RUNS-DESTROYED.md` in that directory.

### 2.2 Incident evidence — `reports/raw/INCIDENT-…`

Seven files: a SQLite ledger, its `-wal`/`-shm` side files, and three logs from
the failed 14 September collection. `.gitignore:82-88` forbids committing
ledgers and logs, and phase 20 §6 **ruled deliberately** that the rule stands:
with the real runs recovered these are debris, and weakening a rule that keeps
ledgers out of the history to preserve debris is the worse trade. Their SHA-256
digests and sizes are recorded in
`reports/incident-fsync-always-raw-destroyed-2026-09-14.md` so they can be
identified if ever cited. Five other files from the same incident — including
`matrix-progress.jsonl`, which carries the traceback — **are** committed.

### 2.3 Build products — `paper/*.{log,blg,bbl,out,aux,pdf-adjacent}`

Regenerated by `scripts/build_paper.sh`. The four PDFs **are** tracked, because
the submitted artefact is the promoted one.

**One asymmetry, recorded as a finding rather than changed here.**
`paper/.build-provenance.json` is ignored at `.gitignore:111` with a reasoned
comment — *"it describes one machine's last build, not the repository's
state"* — while `.build-provenance-anon.json`, `-supp.json` and
`-supp-anon.json` are **tracked** and change on every build. The rule's own
reasoning applies to all four. Either the three should join the first or the
comment is wrong. Not acted on: this pass classifies.

### 2.4 Environment and caches

`.venv/` (6 266), `__pycache__`/`*.pyc` (281), `.pytest_cache/`, `.coverage`,
`junit-local.xml`, `aep_core.egg-info/`. Reconstructed by `uv sync`.

### 2.5 Session and scratch

`.ai/track.md` at five levels (`.gitignore:76`) — an automatic session log, not
authored. `.scratch/` (247) — transient build and probe output;
`make reproduce-smoke` rewrites part of it on every run.

### 2.6 Generated, superseded, or derived scripts

`phase8-driver/.build_keep.sh` — 172 lines, and **not authored**:
`phase8-driver/verify_f0_in_pdf.sh:26` writes it by `sed`-transforming
`scripts/build_paper.sh`. It regenerates on demand and goes stale whenever
`build_paper.sh` changes, which it has repeatedly. The rule at `.gitignore:562`
says exactly this.

### 2.7 Residue

**Paths matching none of the above: zero.**

## 3. Authored work that is ignored

**None.** Every ignored path is raw data, a build product, an environment
artefact, a session log, or a derived script with a stated regeneration source.

This was checked rather than assumed, because phase 21 found
`scripts/lib/results_root_guard.sh` swallowed by `.gitignore:14`'s broad `lib/`
rule — a guard that would have been absent from every clone with nothing in the
diff to say so. The guard now lives at `scripts/results_root_guard.sh` and
`test_the_guard_is_tracked_by_git` asserts it.

**The deposit-critical finding.** The Phase-11 archive was built on 2026-09-03
and covers 20 roots from three trees. **Five referenced trees totalling 852 MB
are not in it**, and two of them back claims the paper makes:

* **`/root/aep-phase14`** — WS-4's write-loss protocol cell, cited in §VI-C.
* **`/root/aep-ws6`** — WS-6's B5 Temporal session, cited in §VI-A.
* `/root/aep-phase13` — the in-flight and armA sessions behind `docs/31`.
* `/root/aep-5b`, `/root/aep-stage3` — a clone and the stage-3 tree.

`reports/raw/ws4-writeloss-s1-2026-09-07/` and
`reports/raw/ws6-b5-s1-2026-09-08-attempt3/` hold the *analysis inputs*
`check_paper_numbers.py` reads, and those are tracked. The **raw runs behind
them are not in the archive and not in git.**

**WS-2 must either extend the archive to cover them or state in `docs/29` that
the deposit is the 2026-09-03 set and name what it excludes.** Depositing the
existing archive without saying so would repeat, at publication scale, the
mistake phase 20 made privately.
