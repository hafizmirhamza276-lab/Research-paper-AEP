## Idea Summary

### Core idea in plain terms

AEP is intended to keep autonomous-agent execution state outside process memory, in one self-hosted Redis instance. A worker acquires a time-limited Redis lease, reads and writes a Pydantic state object, and uses an integer `version` field to reject non-increasing writes. Corrupt or unrecognized state is copied to a poison namespace and surfaced as a typed exception instead of being silently overwritten. The future design would record an intent before a non-idempotent external call so that a crash leaves a detectable ambiguous action for operator/recovery handling.

The three written invariants are:

1. `T_client <= T_lock - Buffer`, with `Buffer >= 15s`.
2. State updates use monotonically increasing integer version checks, not raw overwrites.
3. Corruption, schema mismatch, unknown schema, or ambiguous intent must stop and escalate rather than be guessed away.

### Claimed contribution/novelty as written

The documents do **not** state a formal research hypothesis, novelty claim, or comparison against prior work. The exact headline guarantee repeated in `README.md`, `AEP_IMPLEMENTATION_BRIEF.md`, and both design documents is:

> **Corruption and contention are detectable, and the system fails closed.**

The brief further claims that Phase 1 delivers internal stale-write protection through version checks, while a future intent ledger would make ambiguous external effects detectable. It explicitly disclaims absolute atomicity, split-brain impossibility, HA safety, consensus, and exactly-once external calls. Therefore, the contribution must be assessed as the specific engineering combination and agent-oriented framing of these mechanisms—not as a documented new algorithm.

The implemented deliverable is narrower than the overall idea. `AEP_IMPLEMENTATION_BRIEF.md:20-25` marks the orchestration runner, crash-recovery resolver, and systemic circuit breaker as out of scope. The intent ledger is only an untyped `Dict[str, Any]` field (`src/core/storage.py:100-105`); no write-ahead workflow or recovery policy executes.

## Code Audit

### What is implemented correctly relative to the narrow Phase 1 contract

- The five exception classes and required inheritance exist in `src/core/exceptions.py:12-88`.
- `AEPExecutionState`, `AEPStatus`, timestamps, and the migration registry exist in `src/core/storage.py`.
- State writes go through `_CAS_SCRIPT`; no production raw `SET` to `aep:state:*` was found. Equal/lower versions are rejected, and malformed stored versions return `-2` without overwrite (`src/core/storage.py:138-175`, `:318-384`).
- Reads parse, optionally migrate, validate, verify key/payload identity, and quarantine parse/migration failures (`src/core/storage.py:388-463`).
- Redis lock acquisition uses `SET ... NX EX`; release and renewal use token-checked Lua scripts (`src/core/locks.py:34-69`, `:109-224`). This closely follows Redis's documented single-instance lock pattern.
- The lease heartbeat renews at roughly one-third of TTL and stops renewing at its cap (`src/core/locks.py:228-324`).
- The provided 36 tests all passed when forced to use the available local Redis server; exact environment and limitations are reported below.

### Claim-to-code mismatches and correctness defects

| Finding | Evidence | Consequence |
|---|---|---|
| **The “CAS” is not a true expected-version compare-and-swap and does not fully fence stale writers.** | `_CAS_SCRIPT` accepts any `incoming_version > stored_version` (`src/core/storage.py:157-175`). `version` is caller-controlled and is not issued by the lock service or checked as exactly `stored + 1`. Focused probe: after a newer writer saved v2/`COMPLETED`, a stale v1 snapshot changed to v999/`FAILED`; the write was accepted and final state was v999/`FAILED`. | The broad claim that stale writers cannot silently clobber newer state is false unless every caller obeys an unstated/unenforced exactly-one increment discipline. A stale or buggy writer can jump the counter. `save_state` also does not verify lock ownership. |
| **Lease loss/cap does not stop the protected work.** | On cap or renew `False`, only the background heartbeat returns and logs; the context body is not cancelled or notified (`src/core/locks.py:240-252`, `:288-315`). Probe output showed `ORIGINAL_CONTEXT_ACTIVE_AFTER_CAP=True`, `LOCK_EXPIRED=True`, and `RIVAL_ACQUIRED=True`. | `docs/01-hld.md:420-421`, `docs/02-tech-design.md:1181-1182`, and `tests/MATRIX.md` say work/caller halts or fails closed. In reality, two workers can execute concurrently until the original body exits. This is detect-and-log, not fail-closed execution. |
| **The Timeout Invariant is documentation only.** | No `T_client`, buffer configuration, deadline, cancellation, or inequality check exists in `src/`. Only `ttl_seconds` and docstrings mention the rule. `docs/03-impl-report.md` calls this “enforced by sizing,” but no code enforces it. | External calls can outlive a lease. Phase 1 cannot provide the documented timeout property by itself. |
| **UUIDv4 validation is incorrect.** | `_must_be_uuid4` calls `uuid.UUID(v, version=4)` but never checks the parsed UUID's original version (`src/core/storage.py:117-131`). Probe: a UUIDv1 input was accepted unchanged and retained version nibble 1. | The documented “UUIDv4 enforced” claim is false; UUIDs of other versions and non-canonical UUID-like inputs can pass. Lock/get methods do not validate identifiers at all. |
| **The writer can create state that its own reader immediately quarantines.** | `AEPExecutionState.schema_version` accepts arbitrary strings; `save_state` does not require `CURRENT_SCHEMA_VERSION`. Probe: schema `99.0` was successfully stored, then `get_state` raised `No migration path...`. | The public write API can create an unrecoverable state without transport failure or manual corruption. |
| **Unknown fields are silently discarded.** | No Pydantic `extra="forbid"` configuration exists. Probe: an `unexpected` field was accepted at construction and absent from `model_dump()`. | This conflicts with a strong reading of “schema mismatch fails closed”; misspelled/new fields can disappear silently. |
| **Large integer versions lose ordering precision in Redis Lua.** | Redis Lua numbers are doubles. Probe: increment from `9007199254740992` to `9007199254740993` was rejected as stale. | The claimed monotonic-integer contract has an undocumented safe range (effectively at most exact IEEE-754 integers). |
| **Transport failure during heartbeat is hidden from the lease user.** | `renew_lock` raises `LockAcquisitionError`, but the heartbeat task's exception is later awaited under `contextlib.suppress(Exception)` in `lease` (`src/core/locks.py:303-324`). | The body continues after the lock engine becomes unavailable and may receive no programmatic loss signal, again contradicting fail-closed execution. |
| **No size/resource limits exist.** | `intent_ledger` and `context_data` are unrestricted `Dict[str, Any]`; the full existing payload is JSON-decoded inside Redis Lua on every save. | A large state can consume Redis memory and block Redis's execution thread during Lua/cjson processing. This DoS surface was not identified in the internal security report. |
| **Quarantine is only best-effort and may overwrite same-millisecond evidence.** | Poison key suffix is `int(time.time()*1000)` and a normal `SET` (`src/core/storage.py:555-564`); all failures are logged and swallowed. | Multiple events for the same execution in one millisecond can collide, and Redis failure can leave no forensic record. This is documented partially, but “quarantined” should not be treated as guaranteed. |

### Test-quality and reproducibility audit

- With no `REDIS_URL` and no installed `fakeredis`, `pytest` returns success while skipping every test: `36 skipped` with exit code 0. A naive CI invocation can therefore report green with zero executed tests (`tests/conftest.py:64-75`).

- `test_cas_quarantine_called_on_corrupt` neither requires `StateCorruptionError` nor requires a poison key (`tests/test_cas_write.py:231-243`). It can pass with no tested outcome.
- `test_lease_hard_cap_stops_renewal` reads the lock but never asserts the value; it checks only for a warning (`tests/test_lease.py:100-112`).
- `test_lease_cap_prevents_zombie_renewal` also reads the lock without asserting expiry (`tests/test_lease.py:128-136`). It does not test its stated claim.
- Several quarantine checks are conditional (`if poison_keys`) and therefore do not prove that successful Redis access produces a quarantine record.
- There are no fault-injection tests for Redis disconnect during `save_state`, `get_state`, quarantine, release, or heartbeat; no restart/AOF tests; no schema-cycle test; no payload-size tests; and no hostile-input/property-based tests.
- Dependency ranges are lower-bounded but not locked. There is no lockfile or container. The local run used `redis-py 7.1.0`, `pydantic 2.10.0`, `pytest 8.3.3`, and `pytest-asyncio 1.3.0`; pytest emitted a deprecation warning because `asyncio_default_fixture_loop_scope` is unset.

## Novelty Assessment

A brief literature search was performed on 2026-07-27 using primary papers/preprints and official Redis documentation.

### Strong overlap with established techniques

- **Leases are longstanding.** Gray and Cheriton's 1989 SOSP paper introduced leases as a fault-tolerant distributed consistency mechanism: [Leases: an efficient fault-tolerant mechanism for distributed file cache consistency](https://doi.org/10.1145/74850.74870). Chubby later described a production distributed lock service: [The Chubby Lock Service for Loosely-Coupled Distributed Systems](https://www.usenix.org/conference/osdi-06/chubby-lock-service-loosely-coupled-distributed-systems).
- **The Redis lock code is the documented standard pattern.** Redis's official guidance uses `SET resource random NX PX`, a unique token, and token-checked Lua deletion; it also describes token-checked renewal: [Distributed Locks with Redis](https://redis.io/docs/latest/develop/clients/patterns/distributed-locks/). `src/core/locks.py` closely implements this pattern.
- **Optimistic CAS/version checks are standard.** Redis has long documented `WATCH` as check-and-set optimistic locking: [Redis Transactions](https://redis.io/docs/latest/develop/using-commands/transactions/). AEP's Lua variant packages a full-state version check atomically but does not establish a new concurrency-control principle.
- **Write-ahead logging, intentions, and recovery are established systems concepts.** Beldi logs stateful serverless operations and uses an intent collector to restart stalled functions: [Fault-tolerant and transactional stateful serverless workflows](https://www.usenix.org/conference/osdi20/presentation/zhang-haoran). ExoFlow discusses exactly-once workflow recovery, write-ahead logging, and explicit treatment of external effects: [ExoFlow: A Universal Workflow System for Exactly-Once DAGs](https://www.usenix.org/conference/osdi23/presentation/zhuang). Sagas established long-lived transaction decomposition and compensation in 1987: [Sagas](https://doi.org/10.1145/38714.38742).
- **Agent runtime storage/scheduling is not new by itself.** AIOS includes agent scheduling, context, memory, storage, and access-control services: [AIOS: LLM Agent Operating System](https://arxiv.org/abs/2403.16971) (2024 preprint).
- **Recent agent-specific work is directly close to the external-side-effect concern.** ACRFence identifies replay of irreversible tool effects after agent checkpoint/restore and records those effects to enforce recovery semantics: [ACRFence: Preventing Semantic Rollback Attacks in Agent Checkpoint-Restore](https://arxiv.org/abs/2603.20625) (March 2026 preprint). This substantially overlaps AEP's stated motivation around ambiguous, non-idempotent external tool calls.

Redis's own persistence documentation also confirms that `appendfsync everysec` may lose about one second of data in a disaster: [Redis persistence](https://redis.io/docs/latest/operate/oss_and_stack/management/persistence/). Therefore, storing both state and future intent records in one asynchronously persisted Redis instance cannot by itself guarantee that ambiguity is always detectable after a crash; the tech design acknowledges this residual case at `docs/02-tech-design.md:1284-1287`.

### Where AEP might differ

The potentially distinctive element is the **specific packaging** of a Redis lease, caller-managed version field, poison quarantine, typed failure routing, timeout rule, and proposed intent states for autonomous agents that call legacy APIs without idempotency keys. The repeated refusal to claim exactly-once behavior is also more careful than many engineering descriptions.

That distinction is currently an application-specific synthesis, not demonstrated scientific novelty. The most agent-specific part—the write-ahead intent protocol and reconciliation behavior—is only a future interface contract. No formal model, algorithmic comparison, end-to-end implementation, or experiment shows that this combination yields properties or performance beyond Beldi/ExoFlow-style durable workflows, standard Redis locking/CAS, or recent agent checkpoint-effect fencing. The two focused counterexamples also show that the present implementation does not yet deliver its full written fail-closed/fencing claim.

## Gaps & Risks

### Critical correctness gaps

1. Replace or precisely narrow the stale-writer claim. The current `incoming > stored` rule is bypassable by a version jump; it is not a centrally issued fencing token or an expected-current-version CAS.
2. Make lease loss/cap programmatically stop or cancel the critical section. Logging from a detached heartbeat does not halt work.
3. Implement and enforce the timeout relationship rather than relying on docstrings and callers.
4. Correct UUIDv4 validation and validate identifiers on all public paths.
5. Prevent writers from storing unsupported schema versions and decide whether unknown fields must be rejected.
6. Define the supported numeric version range or change representation/comparison to avoid Lua double-precision failure.

### Missing research system

1. Phase 2—the claimed mechanism for ambiguous external effects—is absent.
2. No end-to-end agent, tool call, legacy API simulator, crash recovery, reconciliation, or operator workflow exists.
3. No formal failure model covers process crash, network partition, Redis outage/restart, delayed response, worker pause, clock skew, or irreversible external effects.
4. Single-instance Redis remains a single point of failure; acknowledged data-loss windows can erase both state and the intent that was supposed to make an action detectable.

### Evaluation gaps

1. No baseline systems or ablations.
2. No Redis 7 target run, multi-process/multi-host workload, repeated race stress, network-fault injection, restart/AOF experiment, or external-side-effect experiment.
3. No realistic workload/dataset or evaluation set.
4. No outcome metrics beyond unit-test pass count.
5. No repeated trials, variance, confidence intervals, significance tests, or power analysis.
6. Several tests have vacuous/conditional assertions and the default configuration can skip all tests with exit code 0.
7. The destructive `FLUSHALL` fixture makes reproduction unsafe on any non-disposable Redis instance.

### Reproducibility and artifact gaps

1. No dependency lockfile, Redis 7 container/configuration, CI workflow, or environment manifest.
2. No raw machine-readable result logs, coverage report, benchmark outputs, or archived scanner reports.
3. No license, citation file, changelog, release tag, or documented artifact-evaluation procedure.
4. Package metadata exposes a top-level package named `src`, and the repository includes stale bytecode/cache artifacts from different pytest versions.
5. The build reports and security scores are internally generated by the same LLM orchestration pipeline and are not independent validation.

## Journal-Readiness Verdict

**Verdict: proof-of-concept software prototype; below workshop-paper level in its current form. It is not close to a strong journal submission.**

The code demonstrates a small subset of the engineering design and passes its narrow unit suite on an available real Redis 3.0 server. That is useful implementation evidence, but it is not a research evaluation. There is no manuscript, explicit hypothesis, formal property, completed central mechanism, baseline, workload, measured system result, or statistical analysis. More importantly, focused probes falsify two central operational interpretations in the current documents: a stale snapshot can overwrite newer state using a higher version, and the lease context continues executing after its lease expires and another worker acquires the lock.

To reach even a credible workshop submission, the project would need, at minimum:

1. A precise research question, threat/failure model, and scoped claims that match executable behavior.
2. Correct fencing/lease-loss semantics and regression tests that fail on the counterexamples in this report.
3. A complete intent-ledger and recovery implementation integrated with non-idempotent external-call simulations.
4. Reproducible Redis 7 packaging and non-vacuous, fail-on-skip CI.
5. Multi-process fault-injection experiments across crashes, delayed calls, connection loss, Redis restart, and concurrent workers.
6. Baselines and ablations—for example, lease only, strict expected-version CAS, durable workflow/intent logging alternatives, and the full AEP combination.
7. Metrics including duplicate-effect rate, undetected ambiguity rate, state-loss/corruption rate, recovery success/latency, throughput, tail latency, and storage/cost overhead over repeated trials.
8. A real related-work section explaining why an agent-specific protocol adds something beyond established leases, optimistic concurrency, WAL/sagas, Beldi/ExoFlow, and recent agent checkpoint-effect fencing.

For a solid conference or journal submission, it would additionally need a substantially broader evaluation, statistically supported results across realistic agent workloads and API failure distributions, an independent artifact review/security assessment, and a clear demonstrated contribution beyond integration of established mechanisms. On the evidence in this folder, the current `>=9` internal build gates should not be interpreted as publication readiness.
