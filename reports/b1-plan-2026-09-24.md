## 1. The scope, and every place that drops it

### 1.1 The claim that is true, in wording a reader can check

From the collected data and §3's fault classes, the defensible statement is:

> **Detection — no undetected duplicate and no lost effect — comes from the
> pre-dispatch record and the no-re-entry transition table, not from the
> durability barrier, for every fault under which the record is still readable
> when recovery runs.** That covers worker `SIGKILL` at all six crash points
> (F1), partitions (F2), worker pauses past lease expiry (F5), and a Redis
> process kill, which the paper shows does not lose acknowledged writes
> (§6.3.3). **It is not established for F3** — a Redis restart that replays an
> AOF missing the record — **and the project's own TLA+ model expects it to
> fail there.**

Why that is the right cut, in the paper's own terms. §3's F3 already says:

> *"**F3** Redis restart with AOF replay. Up to roughly one second of
> acknowledged-but-unsynced writes may be absent under `appendfsync everysec`.
> … The set of faults that can actually realize that loss is narrower than the
> documentation's wording suggests, **and a process kill is not among them; a
> host-level write loss is, and realizes the loss every time.**"

So the manuscript already identifies the fault that destroys the record, and
already says a process kill is not it. Every collected detection cell used a
process kill or a fault with no restart. **The gap is not hidden; it is
unjoined.** §3 also lists as out of model: *"loss of the Redis host once the
fsync acknowledgment has been returned"*.

**The empirical fact that pins it.** In the one regime that destroys unsynced
writes, Redis never restarted:
`reports/raw/ws4-writeloss-s1-2026-09-07/README.md`:

> *"**No void condition fired.** In particular `coordinator_restarted_unexpectedly`
> is `False` in all 60 runs"*

and this is **by construction, not by luck**:
`experiments/harness/redis_kill.py:224` puts the write-loss mechanism in
`NON_KILLING_MECHANISMS`, the set that *skips the restart*. The write-loss
regime was built never to restart Redis. So the record survived in memory and
served recovery, and the zeros in that cell cannot speak to record loss.

## 2. Table 6's restart row

### 2.1 What the config asserts — confirmed

`formal/configs/b3-no-barrier-restart.cfg`:

```
\* EXPECT: fail NoLostEffect
\* B3 with the AOF rewind enabled: the same ablation, now in a run where
\* Redis dies without flushing. This is the pairing that gives the barrier
\* its purpose, and the difference from b3-no-barrier is the whole point of
\* the ablation.
    BarrierEnabled       = FALSE
    SingleTimeline       = FALSE
```

with `NoLostEffect` among the `INVARIANTS`. `SingleTimeline = FALSE` enables
the `Restart` action in the spec:

```
(* F3 -- Redis restarts and replays the AOF.  Enabled only when
   SingleTimeline is FALSE. *)
Restart ==
    /\ ~SingleTimeline
    /\ store' = disk
```

— the in-memory store is replaced by the durable prefix. That is F3, modelled.

### 2.2 The matched pair, which is stronger than the audit stated

The audit reported that the model breaks detection without the barrier. It does
— but the model also contains the **control**, and the two sit two rows apart in
Table 6:

| config | Barrier | TruthfulFsync | SingleTimeline | expectation |
|---|---|---|---|---|
| `b3-no-barrier` | FALSE | TRUE | TRUE | **pass** |
| **`b3-no-barrier-restart`** | **FALSE** | TRUE | **FALSE** | **fail `NoLostEffect`** |
| **`aof-rewind`** | **TRUE** | TRUE | **FALSE** | fail `P1_VersionMonotone` — **`NoLostEffect` HOLDS** |
| `write-loss-no-restart` | TRUE | FALSE | TRUE | pass |
| `write-loss` | TRUE | FALSE | FALSE | fail `NoLostEffect` |

Read rows 2 and 3 together, holding the fault fixed and the fsync truthful:
**barrier off → the effect is lost; barrier on → it is not.** The barrier is
precisely what separates them. That is not "the claim is untested"; it is
**the model predicting the claim is false, with its own control, in the table
the paper already prints.**

Row 5 matters too, and cuts the other way: with a *lying* fsync, the barrier
does **not** save you either. The barrier helps against F3 only when fsync tells
the truth.

### 2.4 What the text would have to say

For the table and the claim to agree, the prose needs three sentences it does
not currently have — placed in §6.3.1, where the claim is made:

> The ablation's null is scoped to faults that leave the record readable. Our

## 3. The missing cell

### 3.1 The trap: the obvious cell does not discriminate

The audit's proposed answer was *"run B3 and AEP-full under `drop_writes` with
a Redis restart after dispatch"*. **That cell would produce a null, and the
project should not be surprised by it.**

`drop_writes` is the *lying* fsync — `TruthfulFsync = FALSE`. With a restart
that is `write-loss.cfg`, which **expects `NoLostEffect` to fail with the
barrier enabled**. So:

- **AEP-full**: WAITAOF returns success, the write was discarded, restart, the
  record is gone → lost effect.
- **B3**: no WAITAOF, the write was discarded anyway, restart, record gone →
  lost effect.

**Both arms lose, and the cell separates nothing.** It is a real result — it
would show that detection fails under record loss for *both* systems — but it
does not test the claim the model actually makes, because the model's
discriminating pair requires a truthful fsync.

### 3.2 The cell that does discriminate

| | |
|---|---|
| **systems** | `AEP_FULL` and `B3_INTENT_NO_BARRIER`, paired |
| **regime** | a new one: record-destroying write loss **followed by a restart** |
| **fault** | the AOF device **fails writes honestly** — `dm-flakey` `error_writes` rather than `drop_writes` — then Redis is killed and restarted |
| **why honest failure** | it is the only realisation on this host in which the barrier can behave as the model's `aof-rewind` row does. With `error_writes` the `WAITAOF` the barrier issues **fails**, so AEP-full withholds dispatch and has no effect to lose; B3 has no barrier, dispatches, and the restart then rewinds the store past its record |
| **predicted outcome** | AEP-full: 0 lost effects. B3: lost effects > 0. That is `b3-no-barrier-restart` vs `aof-rewind`, empirically |
| **crash point** | none needed — the fault is the store's, not the worker's. `redis_kill_point` after dispatch, as the existing redis-kill regimes do |
| **capability class** | `NO_READBACK`, the class where nothing can be reconciled afterwards and a lost effect is therefore observable |
| **runs** | see §3.4 |

**Note what this cell is and is not.** It tests *"can the system lose an effect
when the record is destroyed, and does the barrier prevent it"*. For AEP-full
the mechanism is prevention (the barrier withholds on a failed ack), not
durability. So a clean result **reassigns the claim rather than restoring it**:
it would show the barrier matters under F3, by withholding — which is the
prevention guarantee the paper already has, extended to a fault it has not
tested.

**A second, honest variant** worth pre-registering alongside, because it is the
one the model's `aof-rewind` row literally describes: truthful device, and the
page cache lost. On a single host that means destroying the VM, not the
process — §3.3.

### 3.3 Can the harness already do it?

**Mostly yes, and the two halves already exist separately.**

| piece | status |
|---|---|
| `dm-flakey` provisioning, loop device, `mkfs.ext4`, suspend/reload/resume | **exists** — `experiments/flakey_write_loss.py`, used by WS-4 |
| Kill Redis and restart it, verifying uptime afterwards | **exists** — `experiments/harness/redis_kill.py`, `kill_and_restart`, `docker start`, used by every `redis-kill-*` regime |
| Composing the two | **does not exist, and is deliberately prevented**: `MECHANISM_WRITE_LOSS` is in `NON_KILLING_MECHANISMS` (`redis_kill.py:224`), the set whose members skip the restart |
| `error_writes` mode | **not implemented** — `flakey_write_loss.py:158` builds the table with `" 1 drop_writes"` hard-coded. `dm-flakey` supports `error_writes`; this is a small, contained change |

**What would have to be built:** an `error_writes` table option, a new mechanism
value (say `write-loss-restart`) that is *not* in `NON_KILLING_MECHANISMS`, and
the ordering that the restart happens after dispatch and after the device has
started failing. Perhaps 100–150 lines across two files, plus tests. **No new
concepts.**

**Privileges.** Root is required, and a loop device, and `dm-flakey` — the same
as WS-4: `flakey_write_loss.py` is invoked as `sudo python -m
experiments.flakey_write_loss`, and uses `losetup`, `dmsetup` and `mkfs.ext4`.
Nothing *new* is needed beyond what WS-4 already required.

**One hazard, from WS-4's own docstring:** `dmsetup suspend` calls
`freeze_bdev()`, which **syncs the filesystem** — so provisioning can itself
flush the very writes the cell is trying to lose. WS-4 handles this with
`--noflush --nolockfs`. The new cell must do the same, and the pre-registration
must say so, or it will silently measure nothing.

### 3.4 How many runs, and what each outcome establishes

The prediction is a **separation between two arms on a binary per-execution
outcome**, not an estimate of a rate, so the run count is set by the smallest
separation worth believing rather than by a power calculation for a proportion.

- **30 runs per arm, 10 executions each = 300 executions per arm**, matching
  WS-4's shape exactly (`\WriteLossRunsPerArm` 30, `\WriteLossExecPerArm` 300).
  That is the collection this cell is the sequel to, and matching it means the
  two can be read side by side.
- At 300 executions, a true B3 lost-effect rate of even 5% gives a vanishing
  probability of observing zero, so **B3 at 0/300 would be a genuine refutation
  of the model**, not an underpowered null.
- AEP-full at 0/300 gives a one-sided 95% Wilson upper bound of **1.0%**, the
  same form the paper already uses for its zero-event bounds.

| outcome | what it establishes |
|---|---|
| **AEP 0/300, B3 > 0/300** | The predicted separation. The claim is false under F3 and the barrier is what prevents the loss. §6.3.1 must be rescoped, and the paper gains a positive result: the barrier's value extends beyond prevention-as-measured |
| **Both 0/300** | The fault did not reach the record — almost certainly the `freeze_bdev` sync above, or the restart replaying a complete AOF. **A null here is an instrument failure, not evidence**, and the pre-registration must say so in advance |
| **Both > 0/300** | The barrier does not help under this fault either. The claim is false under F3 and so is the barrier's value there; the honest conclusion narrows both. This is what `drop_writes` would give (§3.1) |
| **AEP > 0, B3 = 0** | Would contradict the model in the opposite direction. Treat as an instrument fault and stop |

### 3.5 Time on this host

WS-4 collected **60 runs in about an hour** (its README records the container
*"healthy for the whole hour"*, and the newest artifact at 11:02:21 UTC).
That is the directly comparable precedent: same fault provisioning, same run
shape.

| | |
|---|---|
| collection, 2 arms × 30 runs × 10 executions | **~1 hour** |
| device provisioning and teardown per session | ~10 minutes |
| **build**: `error_writes` + the new mechanism + tests | **half a day to a day** |
| analysis, verdict script, phase report | 2–3 hours |
| **total** | **roughly 1–2 days of work for ~1 hour of collection** |

The collection is cheap. **The build and the pre-registration are the cost**,
and the risk is the null in row 2 of §3.4 — a day's work that measures nothing
because the filesystem got synced at the wrong moment.

### 3.6 It needs a pre-registration, and here is what it must contain

**Yes.** `docs/26` rule 5 requires one for any new collection, and
`check_prereg_order.py` now enforces it from the data side — a new tracked root
with no `EXPECTED` entry fails the gate. This cell is also exactly the kind the
rule exists for: **a predicted separation, on the paper's central claim, where
a null is the convenient answer.**

Draft contents, `prompts/phase-NN-b1-record-loss-restart-2026-XX-XX.md`:

1. **The question.** Does detection survive a fault that destroys the
   pre-dispatch record, and does the barrier make the difference?
2. **The prediction, as a point prediction, before any data.** AEP-full
   0 lost effects in 300; B3 strictly greater than 0. Derived from
   `b3-no-barrier-restart.cfg` (`EXPECT: fail NoLostEffect`) and
   `aof-rewind.cfg` (`NoLostEffect` holds), which are committed and unchanged.
3. **Scope.** Systems, regime, `NO_READBACK`, runs, executions, seed, and the
   `appendfsync` policy — `everysec`, because `always` would fsync the record
   before the fault and the cell would be vacuous.
4. **The fault, precisely.** `dm-flakey error_writes`; the device starts
   failing after the intent write and before dispatch; Redis is killed and
   restarted after dispatch; `--noflush --nolockfs` on every `dmsetup`
   transition, with the reason.
5. **The instrument-failure condition, named in advance.** If both arms are
   0/300, the cell is void and reported as void — *not* as evidence that
   detection survives. Include the marker-key probe WS-4 used
   (`R10`/`coordinator_restarted_unexpectedly`) inverted: here the restart
   **must** fire, and a run in which it did not is void.
6. **What is reported either way**, including a refutation.
7. **No pooling** with the WS-4 write-loss cell or the matrix: different
   session, different fault, its own macros and its own n — the rule phase 53
   was pre-registered under.
8. **The stop rule** and the spend/time ceiling.
9. **What the manuscript may say** for each outcome, fixed before the data.

## 4. The options

### (i) Rescope the wording only, and state the untested case as a limitation

**Work:** edit the eight locations in §1.2; add the three sentences in §2.4;
one generator edit for the supp Table 4 caption plus a regeneration; rebuild.
**Half a day**, no collection, no root, no new code.

**Cost:** about 70–100 words added to §6 and §9, which the length plan
(`reports/length-plan-2026-09-24.md`) says are already 3.8 and 3.7 pages
against a 12-page budget. And the paper then carries a named, unclosed gap on
its central claim.

**What the paper can then claim:** detection comes from the record and not the
barrier **for faults that leave the record readable**, which is every fault it
measured — a true, checkable, well-evidenced statement. Plus: *our own model
says the barrier is what saves `NoLostEffect` under a restart that rewinds the
store, and we did not test it.*

**How a reviewer reads it:** as honest scoping. The audit's B1 becomes a
limitation the paper states itself, which is the category the audit already
praises this paper for. It does **not** make B1 go away — a reviewer can still
say the headline was oversold in the abstract.

### (ii) Rescope **and** run the missing cell

**Work:** (i), plus §3's build (half a day to a day), a pre-registration, ~1
hour of collection, and 2–3 hours of analysis and reporting. **2–3 days.**

**Cost:** root and `dm-flakey` on the one host; a real chance of the
instrument-failure null (§3.4 row 2); and if the prediction holds, §6.3.1 is
**rewritten rather than trimmed** — the paper gains a result and loses the
clean "detection is free" line.

**What the paper can then claim:** the strongest version — the decomposition is
*complete*, with the boundary measured rather than asserted: the record
delivers detection under record-preserving faults; the barrier delivers it
under record-destroying ones; and here is the cell that separates them.

**How a reviewer reads it:** B1 is answered. The paper's central structural
result stops being "guaranteed by the experiment design" — the audit's sharpest
sentence — and becomes a two-sided claim with a control.

### (iii) A third option, which I think is worth naming: **rescope now, publish the model's prediction as a prediction, and pre-register the cell without running it**

Do (i), and additionally state the matched pair from §2.2 as a **falsifiable
prediction the paper makes about itself**, with the pre-registration committed
and cited. The paper says: our model predicts B3 loses and AEP-full does not
under F3; here is the registered design; we have not run it.

**Work:** (i) plus the pre-registration draft — **one day**, no code, no root,
no collection.

**Cost:** ~120 words instead of ~70. A reviewer may read a registered-but-unrun
experiment as an admission.

**What the paper can then claim:** everything in (i), plus a concrete, dated,
falsifiable commitment that distinguishes "we did not test this" from "we do
not know how to test this". It also front-runs the obvious reviewer request by
showing the design is already worked out.

### Recommendation

**I recommend (iii), with (ii) as the answer if a reviewer asks for it** — and
I want to be explicit that this is a judgement about cost and risk, not a
technical necessity.

The reasoning:

1. **(i) alone leaves the sharpest criticism in the audit unanswered.** "Your
   central structural result is guaranteed by the experiment design" is
   answered by scoping, but only defensively.
2. **(ii) is the right science and the wrong moment.** The build is a day on a
   harness the other session is actively changing (§6, phase 53, the B2
   exclusion), the collection needs root and `dm-flakey` on the single host,
   and §3.4's row 2 says a plausible outcome is a void cell. Starting it now
   competes with the length pass and the deposit, both of which are closer to
   done.
3. **(iii) costs one day and converts the gap from a hole into a commitment.**
   The model already contains the prediction and the control; the paper already
   prints both rows of it in Table 6. Saying so out loud is nearly free, and it
   is strictly more honest than (i) because it states what the project believes
   will happen.
4. **The deciding factor.** §3.1 found that the obvious cell — the one the audit
   proposed — **does not discriminate**. If (ii) had been started on the
   audit's specification it would have produced a null that meant nothing and
   cost two days. That the design needed this much analysis before it was
   right is itself an argument for registering it carefully and running it when
   there is room, rather than rushing it before submission.

**Against my own recommendation, fairly:** if the paper's central contribution
is the decomposition, then a reviewer is entitled to ask why the boundary of
that decomposition was not measured when the fault was already provisioned for
WS-4 and the restart already existed in the harness. (ii) is the answer that
makes B1 disappear rather than shrink. If there is a day and a half of slack
before submission, (ii) is the better paper.

**Not recommended: doing nothing.** Eight unscoped statements against a model
that predicts the opposite is the one position that is indefensible, and it is
the current one.

## 5. What becomes of C4 under each option

C4 as it stands (`paper/sections/01-introduction.tex:115-121`) is **already
correctly scoped** — *"ablating the barrier produces no observed difference in
the crashed-regime detection metrics"* — so C4 is not the problem. The problem
is that the abstract, §6.3.1, §6.3.2, §9.2 and supp Table 4 state C4's finding
without C4's scope.

| option | does C4 survive? | in what form |
|---|---|---|
| **(i)** | **Yes, unchanged.** | Its wording is already the scoped one. What changes is that the rest of the paper stops overclaiming it. C4 becomes *"a decomposition, established for record-preserving faults"* — a narrower contribution than the abstract currently implies, but exactly as strong as its evidence. The phrase **"reassigns our own headline result"** should go: the reassignment is real but partial, and the audit is right that a design-guaranteed null is being presented as a finding |
| **(ii)** | **Yes, and it strengthens.** | C4 becomes a two-sided decomposition with a measured boundary: the record delivers detection under record-preserving faults, the barrier under record-destroying ones. *"Reassigns our own headline result"* becomes defensible, because the reassignment would then be supported by a cell designed to find the opposite |
| **(iii)** | **Yes, as in (i), plus a registered commitment.** | Same as (i), with the addition that the paper names the experiment that would falsify it. C4 reads as *"a decomposition, established for record-preserving faults, with the record-destroying case predicted and registered"* |

**Under every option C4 survives.** What does not survive under any of them is
the unscoped abstract sentence, because it is the one claim in the paper that
the project's own model contradicts.

**One thing to decide alongside, not after.** §6.3.1's *"Durability is neither
necessary nor sufficient for detection"* is the strongest sentence in the paper
and the least defensible. Under (i) and (iii) it must go or be scoped; under
(ii) it is likely to be **false as stated** and should be replaced by the
measured boundary. The audit asked for its removal specifically, and I agree:
it is a general claim built on one regime.
