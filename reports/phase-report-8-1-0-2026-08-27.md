# Phase 8.1.0 — is the fail-closed invariant checkable from the runs already on disk?

**Answer: no.** Four independent reasons, below. Nothing was collected, no
manuscript text was touched, and no macro moved.

This step exists because of a consequence drawn during review of
`reports/plan-phase-8-b2.md`: in the `redis-kill-preack` regime, AEP-full applies
an effect only if `WAITAOF` returned before Redis died, so its applied count
measures how often the ack won a race whose width is the `docker kill` latency.
`\UnwantedPrevented{}` = 28 − (times the ack won) is therefore partly a property
of the fault injector, not of the protocol. The claim that does *not* depend on
that race is the conditional one — **AEP-full never dispatched without a durable
acknowledgement, while B3 dispatched regardless of durability** — and the
question was whether it could be checked against the 150 runs already collected.

---

## A. What was asked, and what was done

Read-only inspection of the 240 Phase 9 runs on this host and the 60 runs of the
2026-08-07 cell in the WSL measurement tree. Specifically: enumerate the event
vocabulary; check the per-execution records for any dispatch or acknowledgement
evidence; trace where `applied` comes from; and trace where the acknowledgement
is issued in the protocol and whether anything observes it.

---

## B. The answer, with the evidence

### B.1 No acknowledgement event exists in any stream

The complete event vocabulary of an AEP-full kill run, across all four streams,
is 23 distinct events. The worker stream — the only one that could witness the
acknowledgement — is exactly:

```
clock_reference   worker_started   composition_validated   execution_started
redis_kill_armed  execution_failed redis_kill_issued       worker_finished
```

Nothing about the barrier, the `WAITAOF`, the `DurabilityAck`, or the dispatch
authorization. The reviewer's reading of the emit list is confirmed.

### B.2 `dispatch_attempts = 0` in all 240 runs

Both arms, applied and not applied alike. The per-execution record does not
capture the dispatch at all, so it cannot distinguish a run that dispatched from
one that did not.

| system | applied | n | `dispatch_attempts` | `outcome_class` |
|---|---|---|---|---|
| AEP_FULL | false | 77 | 0 | DECLARED_AMBIGUOUS |
| AEP_FULL | true | 43 | 0 | DECLARED_AMBIGUOUS |
| B3_INTENT_NO_BARRIER | false | 8 | 0 | DECLARED_AMBIGUOUS |
| B3_INTENT_NO_BARRIER | true | 112 | 0 | DECLARED_AMBIGUOUS |

### B.3 `failure_class` carries no discriminating information

`LockAcquisitionError` in **all 240 runs**, identically across arms and across
applied/not-applied. It is the post-kill failure — Redis is dead, so the next
lock operation fails — and it says nothing about what happened before the kill.

### B.4 `applied` is provider-side and structurally cannot witness the ack

It derives from `oracle_effect_executions` / `oracle_applied_rows` in
`summary.json`, i.e. the mock API's ground-truth ledger. The provider knows a
request arrived. It knows nothing about worker-side authorization. The
authorization itself lives in a Redis key —
`IntentStore.dispatch_authorization_key(execution_id, intent_id)`,
`aep_core/core/intents.py:1076` — which the hard kill destroys and which no run
artifact dumps.

**These four are independent.** Any one of them alone would defeat the check;
all four hold.

## C. It can be added for future runs — in the harness only

The protocol already calls

```python
# aep_core/core/intent_workflow.py:486-494
                    ack=ack,
                    authorization_ttl_ms=required_ttl_ms,
                    connection=connection,
                )

            await self._checkpoint(
                "AFTER_DURABLE_ABOUT_TO_FIRE_BEFORE_PREFLIGHT"
            )
```

immediately after the acknowledgement is issued and the authorization recorded,
and before preflight and dispatch. **Reaching that checkpoint is the ack having
been issued.** `_checkpoint` delegates straight out of the protocol and into the
harness:

```python
# aep_core/core/intent_workflow.py:204-210
    async def _checkpoint(self, name: str) -> None:
        if self.crash_injector is not None:
            ...
            await self.crash_injector.checkpoint(self.crash_point_enum[name])
```

In this regime the installed injector is the `RedisKillInjector`
(`experiments/harness/worker.py:119,127,155`, via `compose_injectors`), whose
`checkpoint()` is documented as *"Called by the protocol at every named
instruction boundary"* and returns early for boundaries it is not armed for
(`experiments/harness/redis_kill.py:260-263`).

**So the harness already receives the post-acknowledgement signal in every kill
run and discards it.** Emitting on traversal is an additive change inside
`experiments/harness/` — **no `aep_core` edit**, which matters because audit
finding **S4-A** was precisely that `aep_core` changed after being certified
untouched. It is not retroactive: it can only help runs collected after it exists.

---

## D. The invariant is one-directional, and confirmatory

**One-directional.** `ack ⇒ applied` is **false**. The kill can land after the
acknowledgement and before transmission, and the harness's crash-point vocabulary
names that exact window: `after_barrier_before_dispatch` maps to
`AFTER_DURABLE_ABOUT_TO_FIRE_BEFORE_PREFLIGHT`
(`experiments/harness/crash_points.py:117-119`). Only `applied ⇒ ack` is claimed,
and any wording implying a biconditional is wrong.

**Confirmatory, not exploratory.** The invariant is enforced in code —
`DispatchAuthorizationError` (`aep_core/core/intents.py:136,1119,1142,1161,1229`)
is raised when the authorization is absent — and `_checkpoint` is awaited on the
protocol path, so `dispatch ⇒ checkpoint traversed` holds by construction.
Observing zero exceptions confirms that the enforcement holds under a real fault,
along a single code path; what it primarily exercises is the harness's emission
fidelity. **It is not an independent discovery of a protocol property**, and this
report says so rather than leaving it to be inferred.

## E. Consequences for the phase

### E.1 The estimand

- **Primary: the covariate-adjusted class effect** — logistic regression of
  applied on capability class, with `log(issue_to_return_ns)` as covariate and
  session as a fixed effect. This is the question B2 exists to answer.
- **Secondary:** the unadjusted within-session paired difference, as a robustness
  check.
- **The invariant is a pre-registered integrity check with a HALT**, not an
  estimand. An earlier draft of the plan made it primary and sized the phase from
  its rule-of-three bound; that was wrong for the reason set out in §D, and is
  corrected.

### E.2 k = 4, derived from the primary estimand

Baseline `p₀ = 53/150 = 0.3533` (AEP-full, NO_READBACK, five sessions). The design
blocks on session and adjusts for kill latency, which is what brings the residual
variance back to roughly binomial — 9C measured over-dispersion 5.37 for
unblocked pooling, **so the binomial calculation is valid only because of the
blocking.** Per-arm n = 30k; 80% power, α = 0.05 two-sided:

| k | n/arm | **MDE (pp)** | secondary half-width (pp) | run time |
|---|---|---|---|---|
| 2 | 60 | 24.4 | 110.8 | 2.4 h |
| 3 | 90 | 20.0 | 30.6 | 3.6 h |
| **4** | **120** | **17.3** | **19.6** | **4.8 h** |
| 5 | 150 | 15.5 | 15.3 | 6.0 h |
| 6 | 180 | 14.1 | 12.9 | 7.1 h |

**Stated minimum detectable class effect: 17.3 percentage points**, which is
**30% of the barrier's own measured effect** (B3 140/150 vs AEP-full 53/150 =
58.0 pp). The paper claims capability class moves the *ambiguity* column by
~100 pp and the *applied* column not at all; a movement of the applied column by
a third of the barrier's own effect would materially qualify that, a smaller one
would not.

k = 4 is also where the primary's MDE (17.3 pp) and the secondary's half-width
(19.6 pp) become commensurable, so the robustness check can corroborate the
primary instead of being decorative. At k = 3 they diverge (20.0 vs 30.6).

**Sensitivity to AUTH's applied fraction**, which is unknown until the first
session:

| AUTH applied fraction | 0.05 | 0.10 | 0.20 | 0.358 | 0.50 | 0.65 |
|---|---|---|---|---|---|---|
| **MDE (pp)** | 13.4 | 14.4 | 15.9 | **17.3** | 17.7 | 17.3 |

**Bounded in [13.4, 17.7] pp across the entire plausible range.** The one input
that could have invalidated the calculation does not. **k = 4 is committed and
will not be extended after seeing results.**

### E.3 The added instrumentation's timing cost — measured

`EventLog.emit` does `json.dumps` + `write` + **`flush()`**
(`experiments/harness/events.py:105-121`); the flush is a real syscall, and the
acknowledgement emit would sit on an awaited call at the exact boundary where the
race is decided. Measured on this host, 2 000 iterations of a representative
364-byte record:

| filesystem | median | p95 | max |
|---|---|---|---|
| ext4 (WSL native) | **5.4 µs** | 11.3 µs | 212.5 µs |
| drvfs (`/mnt/…`, the Windows drive) | **229.7 µs** | 371.9 µs | 2 276.8 µs |

Against the kill-latency envelope (session medians 859–1 216 ms; the
discriminating run-level difference is 194 ms): on ext4 the median cost is
**0.0005%** of the race and **0.003%** of the discriminating difference; on drvfs
the median is **0.02%** of the race and the worst observed case, 2.28 ms, is
**0.23%** of the race and **1.2%** of the difference.

**Both are negligible; ext4 is negligible by three orders of magnitude.**
Buffering is therefore not required — but **collection must run on ext4**, which
drops the cost ~40× and also removes the confound in §F.2.

## F. Findings

**F.1 — `scripts/freeze_results.py` is not portable, and on Windows produces an
unverifiable manifest.** `path.relative_to(root)` yields backslash separators and
`write_text` yields CRLF, so a Windows-generated `SHA256SUMS` reads
`analysis\table-1.csv` with a trailing `\r`. Observed: `sha256sum: WARNING: 16
listed files could not be read`, exit 1, on all four roots. The committed
convention (`experiments/results/matrix/SHA256SUMS`) is forward-slash + LF.
Phase Q's `.gitattributes` fixed the *checkout* direction; this is the
*generation* direction and is unfixed. Worked around in 8.0 by regenerating under
WSL, after which all four verify 16/16 OK. A one-line fix (`as_posix()` and
`newline="\n"`) would close it.

**F.2 — the paper's kill cell and all four replication sessions were collected on
different filesystems, and no config key records it.** The 2026-08-07 cell lives
in `/root/aep` (ext4); the four `b2-*` roots are on the Windows drive, reached
from WSL through drvfs — confirmed by their absence from
`/root/aep/experiments/results`. §E.3 measures a **~40× difference** in
event-log append cost between the two. 9C's "40 of 44 `run-config.json` keys
identical" check is structurally unable to see this, because it is not in the
config; both roots record only the relative path `experiments/results/…`.

This is a **live poolability question for 8.1**, and a candidate partial
explanation for §F.3. **It is stated as a difference to be adjudicated, not as a
demonstrated cause.** Nothing here shows that drvfs latency changes the applied
rate; it shows that the environments differ systematically in a quantity that is
plausibly on the critical path.

**F.2a — and the confound is narrower than F.2 implies, because Redis's storage
was constant across both strata.** Added after review, because the reading in
F.2 is incomplete in a way that overstates the problem.

`compose.phase2.yml:12` mounts Redis's `/data` from a **named Docker volume**,
not a bind mount:

```yaml
    volumes:
      - ./redis/phase2.conf:/usr/local/etc/redis/redis.conf:ro
      - redis-data:/data
```

`docker inspect` confirms what that resolves to on the running container:

```
/data  type=volume  src=/var/lib/docker/volumes/aep-phase2_redis-data/_data
                    name=aep-phase2_redis-data
/usr/local/etc/redis/redis.conf  type=bind  src=D:\...\redis\phase2.conf
```

The AOF that `WAITAOF` waits on therefore lives on **Docker's own storage —
neither drvfs nor the host's ext4** — in every session, and the only bind mount
is the read-only config file. **`WAITAOF` latency was constant across the two
strata**, and the 40× difference measured in §E.3 touched only the harness's
event log, on the observer side of the experiment rather than the mechanism
side.

This *narrows* the confound rather than widening it, and it makes the
"cannot distinguish" reading in §0.6 stronger rather than weaker: the filesystem
difference could not reach the mechanism through the path that matters most.

**But constancy that nobody chose is not a control.** No field records the
backing, nothing holds it fixed, and backlog **B1 breaks it deliberately** — it
bind-mounts Redis's data directory onto a `dm-flakey` device, so B1's numbers
will be collected with Redis storage on a backing unlike every existing number
in the paper, in the one experiment where the storage *is* the fault. Phase 8.2
therefore records `redis_storage_backing` as a second detected field alongside
`results_root_filesystem`, and `docs/24-revision-backlog.md` B1 now *requires*
that phase to read it and state the difference rather than merely have it
recorded.

**F.3 — the session-level ordering is not monotone, correcting the plan's own
earlier claim.** Rev. 2 of the plan reported the kill-latency/applied-count
ordering as "monotonic in all four" Phase 9 sessions. Recovering the fifth
session in 8.0 breaks it:

| session | filesystem | AEP median kill latency | AEP applied |
|---|---|---|---|
| **2026-08-07** (the paper's cell) | **ext4** | **858.9 ms** | **10**/30 |
| `b2-s2-2026-08-21` | drvfs | 880.6 ms | 4/30 |
| `b2-s3-2026-08-21` | drvfs | 945.0 ms | 7/30 |
| `b2-s1-2026-08-21` | drvfs | 1025.2 ms | 12/30 |
| `b2-2026-08-21` (P9-B) | drvfs | 1215.7 ms | 20/30 |

**Spearman ρ falls from 1.000 over four sessions to 0.700 over five.** The
2026-08-07 session has the lowest median latency yet applied more often than two
slower sessions. The four-session claim was true of those four and did not
survive the fifth.

**The run-level result is unaffected and is the one to use.** Over all 150
AEP-full runs: median kill latency 1114.0 ms for runs that applied an effect
against 919.9 ms for those that did not, **+194.1 ms, permutation p = 0.00005**
(20 000 relabellings, seed 4242); B3 control **−12.1 ms, p = 0.76**. 8.1 must
state the mechanism at run level and must **not** claim a monotone session
ordering.

**F.4 — the harness records the kill latency but nothing surfaces it.** Absent
from `RedisKillRecord.echo()` (`redis_kill.py:342-354`) and from every CSV.
Establishing the mechanism required parsing 300 `events.jsonl` files by hand.
9C §6 concluded the provenance gap was the missing Docker daemon state; the more
proximate quantity was already being recorded and discarded.

**F.6 — the submission PDF cannot be built on this machine.** This host's TeX
Live typesets 24 of the 29 `\bibitem` entries `bibtex` correctly produces, so
nine citations render undefined and `check_paper_numbers.py` fails its
`no undefined references or citations` check on a **pristine** tree. CI is green
on the same commits, so CI is currently the only place the bibliography is
correct. Tolerable while CI is the arbiter; not tolerable at submission, because
arXiv builds the source tarball itself and would surface it as a broken
bibliography after the commitment is made. Tracked as backlog **B6** with a
deadline of before Phase 14. Checked and excluded: all 29 keys are in
`refs.bib`, `bibtex` reports `You've used 29 entries`, a manual three-pass build
reproduces it, and ext4 versus drvfs makes no difference.

**F.5 — `seq` is not a total order within a run.** `execution_failed` and
`redis_kill_issued` carry the same `seq` from the same `source` in the runs
inspected — the kill watchdog thread and the event loop race on the counter.
Cosmetic for every number in this report (all events were read by name, not by
order), but `seq` must not be relied on for ordering.
